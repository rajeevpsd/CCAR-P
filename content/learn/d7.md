# Episode 7 – Developer Productivity & Operational Enablement
intro: Episode seven, Developer Productivity and Operational Enablement, is seven percent of the exam. Three parts: setting up Claude tooling for teams, improving developer workflows without lowering the quality bar, and supporting operations so the team can solve problems on its own.

## Part 7.1 – Configure Claude tools and environments for teams
minutes: 7
concepts: Shared configuration; champion-then-batch rollout; four Skill distribution routes; plugins for governed distribution; spend posture; shaping vs. governing layers; hooks; permission modes
example: A release-notes Skill shipped as a flat bundle with no versioning. One bad edit broke output for forty engineers. A group-assigned plugin with versioned updates would have allowed a rollback.
takeaway: Give every developer the same baseline, roll out through champions, govern shared Skills through plugins, and set spend limits before the first bill.
narration:
Configuring Claude for yourself takes minutes. Configuring it for a team means four deliberate decisions.

First, a shared configuration. The team agrees one baseline, with a project CLAUDE.md, an agreed set of tools and MCP servers, and a permission posture, so nobody starts from their own drifting setup.

Second, the rollout. Don't switch everyone on at once. Enable one champion per department, let them prove a real workflow, then spread adoption batch by batch.

Third, how Skills reach people. Organisation-provisioned Skills reach everyone, but have no native rollback. Plugins assigned to a group give you targeting, install preferences and versioned updates from a repository, the strongest governance. Project Skills live in the repository and version with it. API Skills are called by your own products, with version pinning.

Fourth, the spend posture: model defaults, allowlists, effort guidance, and spend and rate caps.

Inside Claude Code, separate the layers that shape behaviour, like CLAUDE.md, Skills, subagents and MCP, from the layers that govern it: hooks, permission modes and sandboxing. If something must always happen, use a hook. An instruction is not a guarantee.

## Part 7.2 – Improve developer workflows using AI-assisted tooling
minutes: 5
concepts: Integrate into existing workflows; writing, reviewing and debugging stages; lumpy adoption; stalling at chat; Diligence; verification checklist; automate checks
example: Generated code passed review and tests, then leaked data through an input it never validated. The author couldn't explain the code.
takeaway: AI-generated code meets the same bar as hand-written code, and the person merging it must understand it.
narration:
AI tooling pays off when it lives inside the workflow developers already use: the editor, code review, and the test loop. Not in a separate chat window they visit now and then. Encode team conventions and review standards as Skills and project configuration, so good practice travels with the tooling.

Claude helps at each stage. Writing: boilerplate, tests and first drafts from a clear spec. Reviewing: summarising diffs and flagging likely issues. Debugging: suggesting hypotheses from a symptom and a trace. But each stage still needs human discipline. Flags are input, not a verdict. Hypotheses get checked against evidence.

Two adoption failures come up again and again. Lumpy adoption, where a few people use the tool heavily and everyone else barely does. And stalling at chat, where the team never moves past asking questions to tool use and repository-aware help.

The safeguard is diligence, turned into a verification checklist: correctness, security, maintainability, and human understanding. Automate whatever you can with tests and evals. And keep one question non-negotiable: can the person merging this explain what it does and why?

## Part 7.3 – Support debugging and operational issue resolution
minutes: 5
concepts: Symptom to architectural cause; common symptom table; runbooks; escalation paths; transient errors and backoff; teach rather than firefight
example: Answer quality slid for a whole quarter because a growing retrieval corpus outpaced the index. A runbook entry for "gradual decline, no code change" would have pointed straight to retrieval drift.
takeaway: Connect the symptom to its cause, fix it once, write it down, and teach the team the path.
narration:
When a live deployment surprises its team, they usually see a symptom, not a cause. The architect's job is to connect the two, and then teach the team how to do it next time.

A few patterns cover most cases. Quality declining slowly with no code change points to a model or prompt change, or to retrieval drift as the corpus grows. Compare against the eval set and check what changed. A latency spike usually means context grew, a tool slowed down, or the cache stopped hitting, so find the slowest span in the trace. Intermittent tool failures point to authorization, rate limits or an unhandled error, so trace one failed call from end to end. And cost rising while usage stays flat means the model tier crept up or caching broke.

For transient errors, like rate limits, timeouts and overload responses, retry with exponential backoff. Don't retry requests that were simply invalid.

Then make the fix last. Write a runbook entry mapping the symptom to the cause and the first action. Define an escalation path: who handles what, and when an issue leaves the team. The goal is a team that only needs you for problems nobody has seen before.
