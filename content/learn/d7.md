# Episode 7 – Developer Productivity & Operations
intro: Episode seven covers developer productivity and operations, seven percent of the exam. Three parts: configuring Claude tooling and environments for a team, improving developer workflows without lowering the quality bar, and supporting debugging and operational issue resolution so the team becomes self-sufficient.

## Part 7.1 – Configure Claude tools and environments for teams (e.g., Claude Code)
minutes: 11
concepts: Shared configuration (project CLAUDE.md, agreed tools and MCP servers, permission posture); champion-per-department rollout in batches; four Skills distribution mechanisms; plugins with install preferences, group targeting and versioned updates; server-managed settings; spend posture (model defaults, allowlists, effort guidance, caps); Claude Code shaping vs. governing layers; six permission modes

decision: Set up a reviewed, versioned shared baseline, roll out through champions and batches, distribute shared Skills through the mechanism that gives the access, versioning and rollback the asset needs, and set the spend posture before the first bill.
takeaway: A shared asset with no version and no way back is a liability the moment more than one person depends on it.
sources: [MODULE 5] Configuring Claude tooling and environments for teams – shared configuration; champions then batches (worked example); Skills distribution table; spend posture; The skill that shipped with no way back; Glossary · [MODULE 1] Claude Code customisation and governance layers; permission modes
narration:
### Configuring for a team is different
You can configure Claude for yourself in minutes. Module five says configuring it for a team is different. You need shared defaults so everyone starts from the same baseline, reusable assets that can be updated and revoked centrally, and spend that stays bounded as usage grows across dozens of people. There are four team-setup decisions the architect owns: environment, rollout, Skills distribution and spend.

### A shared configuration
A team environment is a shared configuration, a baseline everyone starts from instead of a collection of personal setups. For Claude Code, the team agrees a project-level baseline: a shared CLAUDE dot M D, an agreed set of tools and MCP servers, and a permission posture. People start from the same place rather than discovering settings ad hoc and drifting apart. And the baseline is something you can review, version and improve once for everyone.

### The Claude Code layers
Module one gives the vocabulary for what goes into that baseline. Claude Code's layers fall into two groups. Shaping layers set what the agent knows and does. CLAUDE dot M D is loaded at session start with standing instructions, conventions and repo layout. Skills are markdown procedures invoked on demand, such as a commit, push and PR flow, a release-notes generator, or a schema migration. Subagents are isolated helpers for bounded tasks like code review or exploration, often with read-only or restricted tools. MCP servers connect external tools and data, worth it when the same tools should work across clients. Governing layers set what the agent is allowed to touch. Hooks are scripts on lifecycle events, like before or after a tool runs, used as deterministic gates the agent can't skip. Permission boundaries and approval flows decide what runs without prompting. And sandboxing contains the workspace with filesystem boundaries, network egress rules and constrained commands.

### The six permission modes
Module one lists six modes. Default asks before each action. Accept edits approves file edits and common filesystem commands like make directory, touch, remove, move, copy and sed, while other shell commands still prompt. Plan mode locks the session to read-only until the user approves a plan. Auto mode uses a classifier to approve safe actions and block risky ones; the module describes it as a research preview that works on all plans, admin-enabled on Team and Enterprise, defaulting to the Anthropic API, with an environment variable enabling cloud providers. Don't ask auto-denies anything that would prompt and runs only what your allow rules cover, which makes it the mode for locked-down CI. And bypass permissions skips all checks and is scoped to containers or CI only. For a team baseline, the decision is which mode is the default and where stricter or looser modes are allowed.

### Roll out through champions, then batches
Team adoption rarely works as one all-hands switch-on. The pattern that works is a champion per department or team who gets access first, proves the workflow in practice, and then seeds adoption batch by batch. The champion absorbs early friction, builds local examples and becomes the first line of support, so the architect isn't the only person who can answer questions. The module's worked example: a two-hundred-person engineering org wants Claude Code across four departments. One champion per department gets two weeks to convert a real workflow, such as a code-review assist or a test-generation step. Each champion then runs a forty-five-minute session for a first batch of five peers. By the broad rollout, every department has a working example, a local expert and a shared CLAUDE dot M D the champion has already tuned. The same rollout as one mass email would likely produce confused first prompts and a quiet retreat to old habits.

### Distributing Skills to a team
Skills are versioned, reusable procedures. At team scale, the question is how to distribute them: how you create, version and publish a Skill, how access is granted and revoked, and how you roll back if it misbehaves. The module gives four mechanisms.

An org-provisioned Skill, uploaded under organisation settings, Skills, is available to everyone in the organisation at once. Owners manage availability and removal, and users can toggle individual Skills off but can't remove them. There's no version pinning or native rollback; updates mean re-uploading.

A plugin assigned to a group or the organisation bundles one or more Skills for specific teams. Plugins carry governed distribution: install preferences, such as required, installed by default, available, or not available, group targeting, and version-controlled updates from a connected repository. It's the strongest governance option for group-scoped distribution.

A Claude Code project Skill is a filesystem artifact in the repository, in the dot claude slash skills folder. It versions with the repository and is scoped to the projects that carry it, and it rolls back with the repository.

An API Skill is called programmatically by the partner's own products, through the Messages API container, governed in the calling system, with explicit version pinning.

The module adds one distinction: centrally managed Claude Code configuration is a separate channel. Server-managed settings are delivered from Anthropic's servers when users authenticate, refreshing on an hourly polling cycle. That's a settings mechanism, not a Skills distribution path.

### The Skill that shipped with no way back
The cautionary case: a platform team packaged its release-notes procedure as a Skill, bundled it in a plugin and assigned it to its forty-engineer group. A week later a well-meaning edit changed the prompt and the Skill started producing notes in the wrong format for every team that used it. It had been pushed as a flat bundle, without the version-controlled updates and rollback a plugin can provide, so the fix needed a manual re-edit while bad output kept shipping. When a shared asset needs versioning, group targeting or rollback, distribute it inside an organisation-managed plugin and name an owner.

### Set the spend posture before the first bill
Team setup includes cost guardrails, set deliberately rather than inherited. Model defaults: which model a session starts on. Model allowlists and restrictions: which models the team may switch to. Effort guidance: how hard the model works on a task. And spend, rate and per-user caps that keep consumption within bounds. Module two showed that unmanaged model choice can quietly route work to a more expensive tier than needed. At team scale, that multiplies across every member and every request.

## Part 7.2 – Improve developer workflows using AI-assisted tooling
minutes: 10
concepts: Assistance inside the existing workflow (editor, review, tests); encoding team knowledge as Skills and project configuration; writing, reviewing, debugging and the review discipline each needs; lumpy adoption; stalling at basic chat; Diligence; verification checklist (correctness, security, maintainability, human understanding); tests and evals as gates; judgement erosion; coding agent reference architecture
example: A team shipped faster with AI-assisted coding. Three weeks in, a generated change passed review and tests, reached production and leaked data through an unvalidated input. decision: Integrate Claude into the editor, review and test loop the team already uses, hold AI-generated code to the same standard as hand-written code, and turn that standard into a verification checklist backed by automated tests and evals.
takeaway: Access isn't adoption, and speed isn't understanding. A verification checklist turns good intentions into a repeatable gate.
sources: [MODULE 5] Improving developer workflows – integrate into the existing workflow; workflow stage table; two failure modes; Diligence; verification checklist; The merge nobody could explain; cost, complexity, risk · [MODULE 1] Reference architectures – coding agent
narration:
### Configured isn't the same as productive
A team can have Claude configured perfectly and still get little from it. Module five says the difference is the workflow: how AI assistance is woven into the way developers already work, and the discipline that keeps its output trustworthy. The goal is raising the workflow bar without lowering the quality bar.

### Put assistance where the work already happens
AI tooling pays off when it lives inside the existing workflow, the editor, the review process and the test loop, not in a separate chat window developers visit occasionally. The architect's job is to find where assistance removes real friction. Integration is also how a team's knowledge gets encoded. Conventions, review standards and repeated procedures that usually live in people's heads become Skills and project configuration that Claude applies consistently, so good practice travels with the tooling instead of depending on who happens to be in the room.

### Each stage keeps its review discipline
The module's table pairs where Claude helps with the review it still needs. Writing code: Claude drafts boilerplate, tests and first-pass implementations from a clear spec; it still needs correctness and security review, and the author must understand what was generated. Reviewing code: Claude summarises a diff, flags likely issues and explains unfamiliar code; human judgement still makes the call, and AI flags are input, not a verdict. Debugging: Claude proposes hypotheses from a symptom and a trace; you still verify the hypothesis against evidence before acting on it.

### The coding agent shape
Module one's coding-agent reference architecture is the pattern behind good AI-assisted engineering. The work splits in two. First the agent investigates the codebase to understand what must change; that part is agentic, because the path through unfamiliar code can't be written in advance. Then the edits follow deterministic steps: parse, plan, propose, test, review. Subagents handle isolated tasks with enough context but not too much. The failure modes are letting the agent edit and commit without a human review gate, not tracking regression rates against an eval set for each language or framework in the codebase, and treating the whole thing as a conversation instead of a structured pipeline with defined handoffs.

### Two failure modes that keep showing up
Lumpy adoption is when a few developers use the tooling heavily and the rest barely touch it, so the team never realises the gain and practice never standardises. The champion-and-batch rollout from part 7.1 is the fix: it spreads usage deliberately. Stalling at basic chat is when the team uses Claude as a question-answering box and never moves to higher-value workflows like tool use, repository-aware assistance and packaged Skills, because nobody enabled them past the first step. Giving a team access isn't adoption. You have to configure for real enablement inside their workflows.

### Diligence
Diligence is one of the four AI Fluency competencies. Anthropic defines it as taking responsibility for what we do with AI and how we do it; deployment diligence specifically means verifying and vouching for the outputs we use or share. In developer workflows that shows up as a concrete habit: holding AI-generated code to the same standards as any other code, for correctness, security and maintainability, and watching for the subtle failure where engineers accept output they no longer fully understand because it looks right and passes a check.

### The verification checklist
The concrete deliverable diligence produces is a verification checklist: the explicit checks AI-generated output must pass before it reaches production. Each team writes its own, but it should cover four dimensions: correctness, security, maintainability and human understanding. Wherever a check can be automatic, it should be. A regression test suite and an eval set turn correctness and behaviour verification from a reviewer's judgement call into a gate that runs on every change. The checklist defines what must be true; tests and evals prove it repeatably. A team with that checklist has turned a good intention into a gate. A team without it is trusting AI output by default and hoping the reviewer catches what matters.

### The merge nobody could explain
The module's case: a team adopted AI-assisted coding and shipped noticeably faster. Three weeks in, a generated change passed code review and tests and went to production, where it leaked data through an input it never validated. In the post-incident review, the author couldn't explain why the code handled that input the way it did. It looked plausible, the tests were green, and nobody asked the question the checklist would have forced: can the person merging this explain what it does and why? Speed had quietly replaced understanding. That's the judgement erosion diligence exists to catch.

### Cost, complexity, risk
AI assistance lowers the cost of producing code, which raises the volume reaching review; the checklist keeps that volume from overwhelming the quality bar. The hard part is cultural, not technical: holding AI-generated code to the same standard, especially when it ships faster and looks right. And the biggest risk is a team shipping output it no longer understands, until an input nobody reasoned about reaches production.

## Part 7.3 – Support debugging and operational issue resolution
minutes: 9

sources: [MODULE 5] Operational support – support role as translation; symptom to cause to first action table; runbooks and escalation paths; The drift that waited for a quarterly review; Glossary · [MODULE 2] Reliability controls; failure taxonomy; Glossary – transient error, 5xx, rate limit, timeout, exponential backoff
narration:
### The support role is translation
There's always a moment when a live deployment surprises its team. Module five says the architect's role then is to connect what the team is seeing to why it's happening, and to upskill the team so next time they can resolve it themselves. When an issue lands, the team usually reports a symptom, not a cause: latency spiked, outputs degraded, a tool started failing. The architect's value is connecting that operational symptom to its architectural cause, using the same diagnostic discipline from module two. Resolving one incident yourself is firefighting. Teaching the team the symptom-to-cause path they can follow again is support that lasts.

### Symptom, cause, first action
Many symptoms trace to a small set of causes. The module's table is the foundation of a runbook.

Output quality degraded gradually, but there was no code change. The likely cause is a model or prompt change, or retrieval drift as the corpus grew. The first action is to compare against an eval set and check what changed in the model, the prompt or the corpus.

Latency spiked. The likely cause is that context size grew, a tool got slow, or a cache stopped hitting. The first action is to use telemetry and traces to find the slowest span: check token counts per request and the slowest tool call, and confirm cache behaviour.

Intermittent tool failures. The likely cause is authorisation, rate limits or an unhandled error path. The first action is to inspect the failing tool's auth and limits, and trace one failed call end to end.

Cost rose with no change in usage. The likely cause is that the model tier crept up or caching regressed. The first action is to check the per-request model tier and the cache hit rate against the budget model.

### Know your error classes
Module two's glossary gives the vocabulary for reading failures. A transient error is a temporary failure expected to clear on its own, so the same request will probably succeed after a short wait. 5xx errors are server-side failures, such as 500 internal server error, 503 service unavailable and 529 overloaded, usually transient and resolved by retry with backoff, and distinct from 4xx errors, which indicate a problem with the client's request. A rate limit is a cap on requests in a time window; exceeding it usually returns 429, which means throttling rather than failure. A timeout is a request that gets no response within the configured wait. The right response to transient errors is exponential backoff, where each retry waits longer than the last, with a cap on attempts and total wait. And remember the layering: retries near the API call, circuit breakers at the service boundary, fallback chains in orchestration. A 529 at peak that takes down the whole workflow means the fallback was never designed or tested.

### Classify the failure
For quality problems, use module two's taxonomy. A prompt failure is fixed in the prompt. A hallucination is fixed by grounding through retrieval, tools or verification, not a firmer instruction. A model mismatch is fixed by eval-gated model selection. And an orchestrator-workers failure needs a trace that spans the orchestrator and its subagents. Teaching the team to name the class first stops them reaching for the same fix every time.

### Runbooks and escalation paths
Self-sufficiency is engineered. A runbook captures the known symptom-to-cause-to-action paths so the team can resolve recurring issues without the architect. An escalation path names who handles what, and when an issue leaves the team, so people know the boundary of what they can resolve and what must go further. Encourage every team to keep a runbook for its deployment and define a clear escalation path. The goal is a team that needs you only for new problems, not for ones you've already taught them to handle.

### The drift that waited for a quarterly review
The module's case: a support team watched a deployment's dashboards stay green for a whole quarter while answer quality quietly slid. Nobody connected the slow decline to its cause, a growing retrieval corpus the index hadn't kept pace with. The symptoms were visible the whole time. What was missing was the runbook entry saying that gradual quality decline with no code change points at the model, the prompt or retrieval drift. With that path written down, a first-line engineer could have resolved it in an afternoon. Without it, it waited for a review.

### Cost, complexity, risk
Teaching the path takes more of the architect's time up front than fixing the incident directly, but it's the only kind of support that reduces future load instead of repeating it. The hard part is resisting the urge to firefight: the fast fix is doing it yourself; the durable fix is helping the team write the runbook entry and name the escalation path. And the biggest risk is a slow degradation nobody connects to a cause, running until a scheduled review catches it instead of the team catching it the day it starts.
