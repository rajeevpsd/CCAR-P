# Episode 4 – Evaluation, Testing & Optimization
intro: Episode four covers evaluation, testing and optimisation, sixteen percent of the exam. Six parts: defining measurable success criteria across accuracy, latency, cost, safety and security; building eval datasets and test frameworks with the right grading method; running A/B and shadow tests without overclaiming; diagnosing what kind of failure you're looking at; optimising token usage, latency and cost; and monitoring a live system so it can be explained to the business.

## Part 4.1 – Define evaluation metrics (accuracy, latency, cost, safety, security)

narration:
### Why evals come before code
Module two opens with timing. The common approach is to build the system, see if it looks right, and test later. The module argues for the opposite: write the eval suite before production code. Doing so forces three things that are otherwise easy to postpone. You state what success means in measurable terms. You expose design assumptions early, when changing them is cheap. And you give yourself a gate that tells you whether a model swap, a prompt change or a new retrieval strategy actually improved the system. If you can't write an eval for a behaviour, you have no reliable way to know it's present, and every change you make is unverifiable.

### From business requirement to measurable threshold
A requirement like summarise claims accurately doesn't tell you what to measure. The module turns it into an eval criterion in four steps. First, identify the behaviour specifically: extract the filer's name, claim number, incident date and claimed amount from each document. Second, set the threshold. The module's example thresholds are one hundred percent accuracy on structured fields, a hallucination rate below two percent, and responses within schema ninety-nine and a half percent of the time. The crucial point is where those numbers come from: the business requirement, not whatever your first prototype happened to achieve. Third, identify the failure modes: a fabricated claim number, a missing incident date, a value taken from the wrong claim. Each failure mode becomes a category in your eval dataset. Fourth, include adversarial inputs: documents with missing fields, handwritten sections, unusual formatting and non-standard layouts. If your golden dataset has only clean inputs, your scores won't predict production.

### The five dimensions
The exam objective names five dimensions, and module two's exercise shows each one in practice. A regional insurer reads submitted claims, extracts claimant, policy number, loss amount and date of loss, summarises the narrative for an adjuster, and flags claims for possible fraud review. It must respond in seconds, stay within a per-claim cost, never leak one claimant's data into another's summary, and never auto-deny a claim.

Accuracy of field extraction uses a code-based eval: the expected values are known and verifiable by exact or schema match, so a function checks them against ground truth.

Latency uses a code-based eval: p95 is a number, and the check is whether it's under the target.

Safety needs two methods. Code for the deny action, because it's binary: either a denial was issued or it wasn't. An LLM judge for summary faithfulness, because whether the narrative represents the source claim without fabrication is an interpretive judgement a function can't encode.

Security, meaning no cross-claimant leakage, uses a code-based eval: scan each summary for identifiers that appear in any input claim other than the one being processed. It's deterministic.

Cost uses a code-based eval: cost per claim is derived from input tokens, output tokens, model tier and whether caching applies, and the check is whether it exceeds the ceiling.

Notice the pattern. Four of the five dimensions are checked in code. Only the interpretive part of safety needs a judge. That's the grading ladder in action, which is the next part.

### Useful metric vocabulary
The module's glossary gives you precise terms. Hallucination rate is the percentage of responses in which the model invented, inferred or stated information not supported by the input, the source data or the allowed logic. Structured fields are discrete data elements that must be populated in a defined format, like a name, invoice number, date, amount or policy ID, as opposed to free narrative. Schema is the required structure, types and allowed values of the output. And p95 is the latency below which ninety-five percent of requests complete.

### Don't forget the business metric
Module two also says a proof of concept gives you the first signal on whether the system moves the business metric it was designed to improve. Measure that outcome on your POC sample, even before you model production cost. A cost profile that fits the budget on a system that doesn't measurably improve the metric that matters is still a failed deployment. So your metric set has technical dimensions and at least one business outcome.

### Exam signals
If a scenario says the team will measure quality after launch, or set thresholds based on what the prototype achieved, the fix is evals before code with thresholds from the business. If it asks how to check a numeric or structural behaviour, the answer is code. If it asks how to check faithfulness, tone or reasoning, the answer is a calibrated judge.

## Part 4.2 – Design evaluation datasets and test frameworks using mixed methodologies
minutes: 10
concepts: Eval workflow stages: define the task, build the golden dataset, run automated checks, score with a judge, interpret and act; code-based, model-based, human review; grading ladder; judge rigour (rubrics, constrained verdicts, calibration, a different model); volume over perfection; multi-turn evals; keeping the dataset current; per-category scoring
example: A contract review assistant was tested on ten contracts the team knew well. Two weeks after launch it failed on non-standard obligation structures. The eval existed, but its dataset was convenient, not representative, and it had never been updated after the prompt changed.
decision: Build a representative, stratified golden dataset with edge and adversarial cases, grade with the cheapest reliable method on the ladder, calibrate any judge against human labels, and update the dataset with every behaviour change.
takeaway: The highest-risk moment for a regression is when evals exist and are out of date. A stale eval gives false confidence.
sources: [MODULE 2] Evals – workflow table; model-based vs. code-based; grading ladder; judge calibration; evals as the gate; multi-turn evals; cost, complexity, risk; The eval suite that measured the wrong thing · [MODULE 1] Sonnet to Haiku case – stratified sample · [MODULE 5] Verification checklist – tests and evals as gates
narration:
### The eval workflow
Module two lays out a five-stage workflow where each stage produces an artifact for the next. Stage one, define the task: state the behaviour in specific, measurable terms and write the prompt you'll use to test it. A vague definition produces a vague eval. Stage two, build the golden dataset: the inputs your system will meet, including edge cases and counterexamples, labelled with expected outputs. If it isn't representative, the scores aren't meaningful. Stage three, run automated checks: pass each prompt through the system and compare against the expected result. These are fast and cheap, for unambiguous behaviours like format compliance, schema validation and lookups against authoritative data. Stage four, score with a judge: for behaviours that need interpretation, such as tone, reasoning accuracy and edge-case appropriateness, a model-based judge assesses outputs at scale. Stage five, interpret and act: aggregate scores, but look per category. A change that raises the mean while quietly degrading edge cases or adversarial inputs doesn't make the system better.

### Three eval types
There are three ways to grade, with different speed and flexibility trade-offs. Code-based evals run deterministic checks in milliseconds and cost almost nothing: schema validation, regex, JSON parse, length checks, assertions against authoritative data. Their limit is that they can't judge interpretation. Model-based evals give a judge model the original prompt, the output and a rubric, and get back a score and reasoning. They cost roughly a model call per item, and judges can be inconsistent on borderline cases, which is hard to detect unless you force the judge to explain its score. Human review is for high-stakes or novel behaviours where neither code nor a judge can be trusted: safety-critical edge cases, new capability areas without rubrics, or outputs where a wrong grade carries real risk. It's also how you calibrate model-based evals. It's the slowest, most expensive and least scalable option, and humans bring their own inconsistency.

### The grading ladder
Pick the method by climbing a ladder. Use code wherever the behaviour allows it, because it never drifts. Use an LLM judge when the behaviour needs interpretation, and make it rigorous: detailed rubrics, constrained verdicts drawn from a small fixed set of labels instead of free-form scores, calibration against human-labelled examples, and a different model from the one being evaluated, to avoid self-preference. Use human grading as the last resort.

Judge calibration is the step many teams skip. A judge is itself a system that can be wrong. Before trusting it, run it on human-labelled outputs and confirm its agreement with human judgement is high enough. An uncalibrated judge produces confident scores that may mean nothing, which is worse than no automated grade because it seems trustworthy. And favour volume over perfection. Many automatically gradable cases beat a handful of hand-graded ones, because broad, cheap coverage catches more regressions and can run on every change.

### Datasets that represent production
Module one's downgrade case shows good dataset design: two hundred and fifty representative documents with hand-validated targets, stratified by document type, and sized so per-type scores stay meaningful. Stratification is what revealed that two types failed while the average looked acceptable.

### Multi-turn evals
A single-turn eval won't tell you how a system holds up across a conversation. Multi-turn evals are a separate category that score a sequence of exchanges. They check whether the system keeps prior context straight, whether it answers follow-ups without inventing things never said earlier, and whether quality holds as the conversation gets longer. Because the unit is a whole conversation, they need their own golden dataset: full transcripts with known good responses at each turn, covering the follow-ups, topic shifts and conversation lengths the system will see.

### Evals as the gate, and keeping them current
Every change, whether a model swap, a prompt revision, a context strategy change or a retrieval update, should run through the eval suite before it reaches production. The module's example: a team revised a summarisation prompt but didn't update the eval. Everything passed. Two days after release, multi-clause legal sentences were being truncated. The eval predated the change and didn't measure the behaviour that changed.

The postmortem case makes it vivid. A contract review assistant was tested by hand on ten contracts the team knew well, declared ready and shipped. Two weeks later it failed on contracts with non-standard obligation structures, pulling obligations from the wrong section. The eval suite existed, but it was built from those ten convenient contracts, not a representative sample, and when the prompt changed it kept passing because the golden answers still reflected the old prompt. Three decisions led there: convenient inputs instead of representative ones, no dataset update after the prompt change, and manual spot checks treated as a substitute for evals. Spot checks confirm one input produces one output; they can't tell you about inputs you didn't think of.

### Cost, complexity, risk
The module's callouts. Cost: every model-based eval is an API call, but don't let that shrink the eval below what the use case needs. Under-evaluating costs far more. Complexity: eval infrastructure is a parallel system to maintain: the dataset, the judge prompts and the thresholds. Risk: an out-of-date suite gives false confidence, and the highest-risk moment for a regression is when evals exist and are stale.

### Tests as gates in engineering workflows
Module five connects this to developer work. A regression test suite and an eval set turn correctness from a reviewer's judgement call into a gate that runs on every change. The checklist defines what must be true; tests and evals prove it repeatably.

## Part 4.3 – Conduct A/B testing and iterative improvements
minutes: 10
concepts: Hypothesis naming treatment, metric, threshold and constraint; random, session-consistent assignment; primary metric fixed in advance; sample size from minimum detectable effect, baseline and confidence; higher variance in LLM outputs; significance vs. practical size; secondary metrics; interaction with input types; shadow testing; offline scoring
example: A team compared 50 sessions of a new prompt with 50 of the old one, saw 68% vs. 62% task success, and shipped. Two weeks later success settled at 61%. The sample was too small, the inputs weren't balanced, and the metric was chosen after the results.
decision: Pre-register the hypothesis, primary metric and sample size; randomise consistently per user or session; and use shadow testing when one bad output is too risky or traffic is too low for a live split.
takeaway: An underpowered test with the metric picked afterwards produces confirmation, not evidence. Decide the metric and sample size before you look.
sources: [MODULE 2] A/B & Obs – structured A/B testing table; reading results without overclaiming; shadow testing; The 50-session winner that wasn't; experiment-design plane checkpoint; cost and risk callouts
narration:
### Why LLM experiments are harder
Integration gets Claude into the stack. The next question is whether changes to it actually help. Module two treats A/B testing for Claude like any experiment, with one important difference: LLM outputs are probabilistic, so results are noisier and interaction effects are harder to control.

### The four components
A structured test needs four things, and the module says what goes wrong without each.

A hypothesis: a specific, falsifiable statement naming the treatment, the expected direction of the primary metric and any constraints on secondary metrics. The new prompt is better fails, because it names no treatment, metric or threshold. A usable version reads like: replacing the instruction to summarise with an instruction to extract the three most important action items will increase task success by at least five percent without degrading p95 latency. Without a hypothesis, any result can be read as a win, because you can always find some metric that moved the right way.

Treatment and control assignment: random assignment of requests to the new or current version, and consistent for a given user or session to avoid contamination. Non-random assignment makes the groups incomparable; if the treatment happened to get simpler queries, the win may be an artifact.

A primary metric, defined before the experiment runs: task success rate, cost per completion, p95 latency or a satisfaction proxy. Choosing it after seeing results is outcome shopping, and turns an experiment into a retrospective correlation.

A sample size calculated from the minimum detectable effect, the baseline value and the required confidence. LLM outputs vary more than deterministic systems, so the sample needs to be larger. An underpowered test can't tell a real effect from noise, and a team that runs until it sees what it wants will find it, real or not.

### Reading the result without overclaiming
Statistical significance means a result is unlikely to be chance at that sample size. Whether it's big enough to matter is a separate question; a significant change can still be too small to justify the cost of shipping and maintaining a new version. Before declaring a winner, ask two questions. Is the effect large enough to justify the operational overhead? And did any secondary metric degrade? A prompt that lifts task success while raising cost thirty percent may not be a net win, depending on the budget.

LLM experiments add one more failure mode: interaction between the treatment and specific input types. A change that helps typical inputs may hurt rare edge cases that barely appear in the test period but show up in a later seasonal spike. So aligning the test period and input distribution with real traffic matters more here than in most software.

### The 50-session winner that wasn't
The module's case: a support team ran a revised system-prompt instruction on fifty sessions and the old version on fifty. Task success was sixty-eight percent against sixty-two. They declared a winner and deployed. Two weeks later the new version had settled at sixty-one percent; the gain vanished. Three problems, any one enough to invalidate it. The sample was too small: a six-point difference on a high-variance metric needs hundreds per group. The input distribution wasn't controlled: the treatment group happened to get fewer edge cases. And the primary metric wasn't fixed in advance: they looked at task success because it moved the right way, and would have looked elsewhere if it hadn't.

### Shadow testing
A live A/B test sends real users to the new version, so a regression reaches some of them before the experiment closes. Shadow testing avoids that exposure. Run the new version in parallel, send it a copy of live requests, and serve every user the current version's response. Log the shadow outputs instead of returning them, and score them offline. The deployment decision is made before any user has seen the new version.

Choose between them by risk and traffic. Use a live A/B test when the deployment can absorb a small, bounded exposure to a worse version and traffic is high enough to reach a meaningful sample in a reasonable time; you get real downstream signals, like whether users accepted the answer. Use shadow testing when one bad output carries too much risk, or traffic is too low to support a live split before the change is needed. The cost is losing downstream signal, so scoring relies on an offline rubric or golden answers. In regulated deployments, where exposing users to an unvalidated change may not be allowed at all, shadow testing is often the only acceptable option.

### Planning the experiment
The module's experiment-design plane uses two axes: the expected effect size and the confidence you need before acting. A small expected effect with a high confidence requirement needs the largest sample and the most careful design. A large effect with a modest confidence need can be detected with a smaller sample. Placing a scenario on that plane tells you the posture and the minimum sample size.

### Iterating
Iteration means one change at a time, each tested against a pre-set hypothesis, with the eval suite as a gate before any live test. The cost callout says it plainly: without a pre-specified metric you'll always find a result you like, and an underpowered win leaves you maintaining a version no better than what it replaced.

## Part 4.4 – Diagnose system issues (prompt failure, hallucinations, model mismatch)
minutes: 8
concepts: Classify before fixing; prompt failure; hallucination; model mismatch; orchestrator-workers failure; change attribution (model drift, data drift, model update); symptom to cause to first action; underspecification; Discernment
example: After a cost-driven swap to Haiku, two document types began returning wrong fields. The team first strengthened the prompt with no effect. Classifying it as model mismatch pointed to re-running the eval per category and routing those types back to Sonnet.

takeaway: Each failure class has its own fix. A stronger instruction won't cure a hallucination, and a better prompt won't fix the wrong model.
sources: [MODULE 2] A failure taxonomy; Observability – change attribution; Discernment · [MODULE 5] Symptom to likely cause to first action table · [MODULE 1] Prompting as Architecture – underspecification; [EXAM GUIDE] Sample question 3 · example is illustrative [INFERENCE]
narration:
### Classify before you fix
Instrumentation tells you a metric moved. Diagnosis tells you what kind of failure moved it. Module two's advice is to classify the failure before attributing a change, because the common classes are distinct and call for different fixes. Teams that skip classification tend to try the fix they know, usually a prompt tweak, whatever the cause.

### The four failure classes
A prompt failure means the instruction was ambiguous or underspecified and the model filled the gap. The fix is in the prompt, not the model. This links straight to module one's underspecification: where the prompt is silent, the model improvises, differently each time. The fix is to make the implicit explicit: name the scope, the format and the constraints, and restate the goal.

A hallucination means the model produced confident, fluent content that isn't grounded in the input or a reliable source. The fix is grounding: retrieval, tool use or verification. The module is explicit that a stronger instruction won't resolve it. This is the next-token-prediction and knowledge properties showing up in production.

A model mismatch means the chosen tier is wrong for the task, or it was swapped without re-evaluation. The fix is model selection, gated by an eval. The classic signature is a system that worked on one tier and degraded after a cheaper swap, often in specific categories.

An orchestrator-workers failure appears in multi-agent systems. Trace across the orchestrator and its subagents. A recoverable subagent failure, which you retry or flag, looks different from an unrecoverable orchestrator failure. Attribution needs a trace that spans both.

### Change attribution
When a metric moves over time, module two adds three causes to separate. Model drift: behaviour on stable inputs changed. Data drift: the input distribution changed. Model update effects: the version changed and behaves differently on existing inputs. Each has a different mitigation. You can only tell them apart if your traces record the model version and you can compare input distributions over time.

### Symptom to cause to first action
Module five turns this into a runbook-style table, which is worth knowing almost word for word.

Output quality degraded gradually with no code change: the likely cause is a model or prompt change, or retrieval drift as the corpus grew. First action: compare against an eval set and check what changed in the model, prompt or corpus.

Latency spiked: context size grew, a tool got slow, or a cache stopped hitting. First action: use telemetry and traces to find the slowest span, check token counts per request and the slowest tool call, and confirm cache behaviour.

Intermittent tool failures: authorisation, rate limits, or an unhandled error path. First action: inspect the failing tool's auth and limits, and trace one failed call end to end.

Cost rose with no usage change: the model tier crept up, or caching regressed. First action: check the per-request model tier and cache hit rate against the budget model.

### Discernment
Module two names the competency behind good diagnosis: Discernment, the discipline of judging the quality of what the model produced rather than accepting it at face value. In production, that means classifying outputs as acceptable, needing revision, or needing override, and feeding that judgement back into evals and monitoring. A team without Discernment watches metrics move and never asks whether the outputs were actually good.

### Working an exam scenario
Exam diagnosis questions usually include a tempting wrong fix. If the symptom is fabricated details with no grounding in the source, the right move is grounding through retrieval, a tool or a verifier, not a firmer instruction. If quality dropped right after a tier change and only in certain categories, it's model mismatch: re-run the eval per category and consider partial routing. If outputs vary because the prompt never stated the format, it's a prompt failure. If a multi-agent run produced a confident but incomplete answer, trace across levels and check coverage. Say the class first, then the fix.

## Part 4.5 – Optimize token usage, latency, and cost-performance trade-offs
minutes: 9
concepts: Cost model: volume × (input tokens × input rate + output tokens × output rate), cached tokens at the read rate; distribution not average; p95; prompt caching; Batch API for asynchronous work; max_tokens cap; per-step tiering; progressive context; extended thinking only on a measured gap; sensitivity analysis
example: A document triage system's POC bill was negligible, but in production the long-document tail consumed 80% of token spend, and a 529 at peak took the whole workflow down. Modelling the distribution, caching the stable prefix, moving async work to Batch and adding a fallback chain fixed both.
decision: Model cost from the token distribution at production volume before choosing the architecture, then apply the levers in order of payoff: tiering, caching, context strategy, output caps, Batch for asynchronous work, and thinking only where it earns its cost.
takeaway: A POC answers "can it do this?", not "what does it cost at scale?". Model the distribution and run sensitivity before you commit.
sources: [MODULE 2] POC to Prod – cost and latency modelling, caching, reliability; The demo cost profile that became the production bill; Sizing – steps 1 to 4, Batch API, caching details · [MODULE 1] Caching mechanics; Opus-everywhere case; [EXAM GUIDE] Sample question 2
narration:
### The POC-to-production gap
Your eval suite tells you whether the system behaves correctly. It says nothing about whether it can afford to behave correctly at the volume the partner expects. Module two calls this the POC-to-production gap, and it has four dimensions that are invisible in a demo: cost, latency, reliability and failure modes. A POC running ten to fifty requests a day produces a negligible bill. A demo runs one request at a time, so it shows median latency, not p95 under load. A POC has no retries or fallbacks, because a developer just refreshes. And a demo is tested on inputs the developer expected.

### Build the cost model before the architecture
Three inputs drive the model: call volume, the token budget per request, and the model tier. Module two's sizing steps make it concrete. Get call volume from the business owner, not from intuition or a sample dataset, including multi-turn continuation calls. Set the token budget as input tokens, meaning system prompt, retrieved context and user message, plus expected output tokens, and model the distribution rather than the average. Then project monthly cost: volume times input tokens at the input rate, plus volume times output tokens at the output rate, since input and output are priced differently on every tier. Use the cache read rate for cached input tokens. Compare the result to the ceiling, and if it's over, change the architecture before writing code. Finally, run sensitivity analysis: what if volume doubles, or the distribution shifts toward the tail?

### Why averages lie
Token distributions are usually skewed. Most requests are short, but a tail of long ones consumes a disproportionate share. A model built on averages can underestimate cost by a factor of two or three. The module's post-launch quotes make it real. One: raw demo costs presented without scaling to production volume, with error bounds, is where the risk lives. Two: we assumed the token distribution would be uniform; the long documents in the tail consumed eighty percent of total spend. Three: when the endpoint returned a 529 at peak on day three, the whole workflow went down, because the team had never tested what happened when a call failed. All three share a root cause: the POC was treated as a cost and reliability model, not a capability demonstration.

### The levers, in order
Per-step model tiering, validated by evals, is usually the biggest lever; the Opus-everywhere case cut cost seventy-one percent with no satisfaction change.

Prompt caching is the most effective lever when the system prompt is long and stable. It preserves the processed prefix so the API doesn't reprocess it. Savings scale with prefix length and reuse. Static content goes first, then the breakpoint, then dynamic content. It needs explicit cache control markers, writes cost more than standard input, reads are much cheaper, which the module illustrates as ten percent and says to verify, and the default TTL is five minutes, so infrequent workloads may not benefit. If cached content must reflect live state, caching creates a consistency window.

Context strategy: progressive instead of monolithic, with compaction for long sessions, because cost scales linearly with input.

The max tokens cap and output length, because output tokens are priced higher and long outputs add latency.

The Batch API for work that can run asynchronously. The module illustrates a fifty percent discount and up to a hundred thousand requests per batch and tells you to confirm the current figures. Model it as an alternative wherever the SLA allows asynchronous processing, and for regulated workloads check whether batch processing is covered by the BAA and compliance configuration before routing protected data through it.

Extended thinking only on a measured accuracy gap.

### Reliability is part of cost-performance
Optimisation isn't only about spend. Module two's reliability controls protect performance under failure: retries with exponential backoff close to the API call, circuit breakers at the service boundary, and fallback chains in the orchestration layer. A system with no fallback has one point of failure, the primary endpoint, and when it fails at peak the whole workflow fails instead of degrading.

### The exam's sample question
The exam guide's second sample question is in this territory: a large, stable instruction block called often, with a cost problem. The answer pattern is static first, breakpoint, dynamic last, and check that the call frequency actually makes caching pay.

### Traps
Optimising the average instead of the tail. Turning caching on where the prefix changes every call. Assuming a longer TTL fixes a prefix that keeps changing. Moving to a cheaper tier without a per-category eval. And presenting demo costs to a client without scaling them to production volume.

narration:
### What monitoring must answer
Part 3.4 covered how to design observability at scale. This part is about running it: what you watch day to day, how it reaches the people who funded the system, and how a signal turns into action. The four questions still frame it: what is the system doing, how well is it performing, when did it change, and why did it change?

### The production dashboard
Module two's metric layer gives you the core dashboard. Cost per request. Latency at p50 and p95. Task success rate, where the downstream system provides an acceptance signal. And error rate by error type, because a spike in 429 rate limits needs a different response from a rise in 5xx server errors. Underneath sits per-request decomposition, because aggregate metrics can look healthy while a small fraction of requests consumes most of the budget and produces wrong answers.

### Alerts and distribution checks
Set threshold alerts on what matters. The module's examples: a cost spike above one hundred and fifty percent of the seven-day average, and p95 crossing the SLA threshold. Model drift is gradual and slips under thresholds, so compare output distributions periodically. And when something moves, attribute it to model drift, data drift or a model update, because each has a different fix.

### The translation layer
The people who funded the deployment aren't reading request traces. They read a KPI dashboard that tracks the outcome the system was meant to improve. So module two calls for a translation layer that connects technical metrics to business metrics. For a customer service agent, the business metrics might be average handle time, first-contact resolution and customer satisfaction. The observability stack measures latency, task success and error rate. The translation layer maps task success to first-contact resolution and latency to handle time, so the business owner can see whether the system moves their numbers. Build it at design time. Otherwise the first business review asks what's driving the change in handle time, and answering it means a retrospective reconstruction instead of a live query.

### Monitoring is not a feedback loop
Module four draws the line that the exam tests. A dashboard collects and displays signals. A feedback loop maps each signal to a trigger, an owner and a required action: signals, triage, decide, act, review. Its case lays an alert log beside a stakeholder review calendar over ninety days. Weeks one to three, everything is steady. Weeks four to seven, the eval score drifts down week after week, but the error rate stays flat, so no hard alert fires, and no review is held. Weeks eight to twelve, the score keeps falling and the stakeholder says output is less useful lately; the quarterly review finally surfaces it in week twelve. A quality-drift trigger should have escalated to an architect review by week five. Every signal existed. Nothing decided they mattered.

### Runbooks close the loop for the team
Module five tells the same story from the operations side. A support team watched dashboards stay green for a quarter while answer quality slid. The cause was a growing retrieval corpus the index hadn't kept pace with. The symptoms were visible the whole time, but the runbook entry, gradual quality decline with no code change points at the model, the prompt or retrieval drift, was missing. With it, a first-line engineer could have fixed it in an afternoon. So monitoring has three parts: instrumentation that collects the right signals, a governance table that turns them into triggers and owners, and runbooks that tell the owner what to do.

### Regulated monitoring
For regulated deployments, some reviews run on a schedule regardless of the metrics, such as periodic output audits against a documentation standard or scheduled residency confirmation. You'll see these in episode six's governance table. Monitoring design has to include them.

### Exam signals
If a scenario describes green dashboards and unhappy users, or a slow decline that no alert caught, the answer is a decision layer: a drift trigger with an owner and a runbook action. If it describes a sponsor who can't see value in technical metrics, the answer is the translation layer. If it describes a cost spike nobody can explain, the answer is per-request decomposition.
