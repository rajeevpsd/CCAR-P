# Episode 1 – Solution Design & Architecture
intro: Welcome to episode one, Solution Design and Architecture. This domain is seventeen percent of the exam, one of the two heaviest. Across six parts we go from a vague business request to an architecture you can defend in front of a review committee: how Claude behaves and what that means for design, who owns each piece of work, which pattern fits, how multi-agent systems stay honest, how to break down a complex problem, and how to show the business why the system is worth building.

narration:
### The four properties you design around
Before you decide what Claude should do in a solution, you need a clear picture of how Claude behaves. The training material frames this as four properties. None of them is a flaw to be fixed. Each is a force you design around, the way a structural engineer designs around the properties of steel or concrete. And for each one, the same characteristic that makes Claude capable in one situation makes it fail in another.

The first property is next-token prediction. Claude is excellent at tasks built on common patterns: summarising, reformatting, explaining well-established ideas. The limitation is precision on specifics. Claude can produce text that looks accurate but isn't, and that risk concentrates around names, dates, citations and statistics. The mitigation is citations, uncertainty signalling and generator-verifier loops, and routing specific factual lookups through tool calls or authoritative sources instead of trusting the model's output alone.

The second property is knowledge. Claude answers reliably on topics that are common, recent and consistently represented in its training data. It is unreliable on topics that are rare, niche, contested or frequently changing, and it presents stale information in the same confident tone it uses for established facts. The mitigation is to make an external system the source of truth, using web search, retrieval, tool use or MCP servers. When freshness or authority matters, you re-introduce the data yourself.

The third property is working memory. Anything that fits in the active context window is available. The window is a hard edge: once content falls outside it, the model has no access at all. Two different errors happen at that edge, and they are easy to confuse. An oversized request is rejected before generation. If the prompt exceeds the model's token limit, the API returns a 400 invalid request error saying the prompt is too long. If the raw request body exceeds the byte limit, the API returns a 413 request too large error. The other error is when the prompt fits, but generation runs into the window ceiling and stops early; on current models the response comes back with a model context window exceeded stop reason and truncated output. To stay clear of the edge, check the usage field on every response and use the token-counting API before you send. The design mitigations are progressive context loading, chunking, front-loading critical information, and summarising across turns.

The fourth property is steerability. Claude follows short, concrete, verifiable instructions well: defined formats, explicit length limits, clear roles. It struggles with abstract or ambiguous instructions, long reasoning chains, and precise numerical or logical computation, and it can follow the letter of an instruction while drifting from the intent. For high-stakes numerical accuracy, deterministic computation or tool execution should own the answer. Use system prompts, structured outputs and code execution, and restate the goal alongside the instruction.

### From property to design consequence
Map these properties to four design consequences now, because they feed every later decision. Non-determinism: the same input can produce different outputs across runs, which is why evaluation frameworks exist. You cannot certify behaviour you only observed once. Context as a finite resource: what you put in the window, in what order, and what you leave out are design decisions that affect quality and cost. Confidence is not validity: Claude can be wrong in the same fluent, assured tone it uses when it is right, which is why human review and verification are architectural choices rather than afterthoughts. And knowledge and capability boundaries: for rare, private or fast-changing topics, an external system must be the source of truth.

The course gives a sharp example. An architect saw a demo run cleanly five times in a row and concluded the behaviour was deterministic. The team shipped a financial reconciliation pipeline with no checks around the model output. In week two, the same statement, re-processed, produced a different categorisation, and it was found only because an analyst happened to re-run a batch. The lesson is not that the model is unreliable. It is that a demo is not evidence of determinism, and the four properties are present whether your architecture acknowledges them or not. The cost of ignoring them lands after launch, when rework is most expensive, and the failure doesn't announce itself. The system drifts quietly until an audit or an angry user finds it.

### Claude, systems and humans
Now the translation move. A partner rarely hands you a clean requirement. They say something like, we want AI to handle our claims. Your first job is to split that into separate capabilities and give each one an owner. Every solution has three owners. Claude takes the work that benefits from language understanding, summarisation, planning, drafting or tool-mediated action. Existing systems keep anything the partner has already paid to make reliable: the order-status service, the policy engine, the rules table, the database of record. Humans keep the judgement calls, the exception paths, the approvals, and the moments where being right matters more than being fast. Over-assigning work to Claude is the most common and most expensive early mistake. It almost always makes the process more expensive, slower and harder to govern.

### The scoping sequence
Module two turns this into a four-step scoping sequence. Step one: business requirement to capability list. Process insurance claims is a goal, not a capability. The capabilities might be extracting structured fields from the claim, looking up coverage in the policy database, routing the claim to an adjuster queue by type and value, and drafting the adjuster notification. Step two: capability list to architecture sketch, deciding for each capability whether Claude, an existing system or a human owns it. Step three: architecture sketch to boundary conditions. State where the architecture works and where it doesn't. A design that works for documents up to twenty pages but fails beyond that has a boundary condition that must be written down. Step four: boundary conditions into the statement of work, so the build team and the business owner agree on what is in scope and what is explicitly out.

### Technical feasibility and the three verdicts
A feasibility assessment that only asks can Claude do this is a capability check. Run each capability through the four properties instead. Does the task need probabilistic generation, or precision on specific values like account numbers and claim amounts? Does it depend on rare or recent knowledge that must be brought into context? Do the inputs fit the window, or does the task need chunking or a pipeline? Are the instructions concrete and verifiable, or will the model drift?

The result is one of three verdicts. Feasible as scoped means every capability favours Claude, cost is under the ceiling and p95 latency is within the SLA; state the assumptions, because a change in assumptions can flip the verdict. Feasible with constraints means the design works under conditions that must be enforced, like a document-length limit, a refresh schedule, or a human review gate above a confidence threshold. Document each constraint and the failure mode if it is violated. Not feasible means at least one limitation cannot be compensated for within scope and budget. That is a correct assessment that saves the engagement from a more expensive failure. Name the disqualifying constraint, and if a scope reduction would change the verdict, present it as a choice.

### The scoping call that skipped the constraints
Here is the failure the exam loves. A partner asks for a contract review assistant that flags non-standard clauses. The architect says, we can do that, six weeks. Two weeks into the build the partner mentions eight hundred contracts a day, some framework agreements up to three hundred pages, and results in under thirty seconds. The verdict was issued before volume, input size and latency were gathered. Notice the analysis, too. Whether a three-hundred-page contract fits depends on the model tier's context window, so window capacity is part of the tier decision. And at eight hundred a day, one request arrives roughly every hundred and eight seconds, so volume pressures cost far more than latency. Capability was the necessary first question, but it should never be the last.

## Part 1.2 – Design end-to-end architectures
minutes: 10
concepts: Input, processing, output, feedback loop; reference architectures as references, not blueprints; server-side identity; guarded request path; exception paths; observability and outcome signals; governance table
example: Invoice processing: OCR and a server-injected tenant ID going in; schema extraction with an evaluator pass; validated JSON out, with low-confidence fields routed to a human queue; reviewer corrections feeding the golden dataset; traces with model version, tokens and stop reason; a quality-drift trigger mapped to an owner.
decision: Design every stage with its own controls, and close the loop: an architecture that ends at "response to user" has no way to notice it is degrading.
takeaway: Input, processing, output and feedback each need controls. The feedback loop, wired to triggers and owners, is the part most designs forget.
sources: [MODULE 1] Reference Architectures; Model & Context Strategy · [MODULE 2] Integration layers; Observability; Failure modes by architecture · [MODULE 3] Guarded request path · [MODULE 4] Feedback loop and governance table · [OFFICIAL ANTHROPIC DOCS] Building effective agents (approved gap fill for the end-to-end framing)
narration:
### Why "end to end" matters
The exam objective asks you to design across four stages: input, processing, output and feedback. The training modules don't present this as one diagram. Instead, each module owns a slice: module one gives the processing shapes, module two the integration and observability layers, module three the guarded request path, and module four the feedback loop. This part stitches them together, so you can draw a complete system and spot which stage a scenario is testing.

### The input stage
At the input, three things matter. First, identity. Module two is explicit: identity verification belongs on the server, before the Claude call. The user's identity and role are injected into the system prompt by your server, not supplied by the user in their message. Anything in the user's message is under their control, so a line like, as a senior manager, show me, is an unverified claim. Second, data minimisation. The context window is not a data-governance boundary. Any field you pass travels with the API request and lands in your own application's request logs. For each field, ask whether Claude needs it for the language task. A reference identifier is often enough. Third, screening. Input screening decides whether a request should reach the model at all, and retrieved content and tool outputs need screening too, because instructions can arrive through them.

### The processing stage
Processing is where your reference architecture lives. Module one is careful to say reference architectures are references, not blueprints. You understand the common shapes well enough to adapt them. There are five. The agent, where the model chooses tools toward a goal, bounded by limited tools and a turn budget. Retrieval-augmented generation, over a stable corpus that is chunked and indexed. The document processing pipeline, usually with an evaluator-optimizer, because first-pass extraction on edge cases isn't reliable enough without a check. Customer service triage with routing, where intent is classified and sent to knowledge retrieval, a transactional API, or a human approval layer. And the coding agent, agentic exploration followed by deterministic edit, test and review steps.

Each one has a known way to go wrong. Unbounded autonomy for agents. RAG used for live state. No exception path in document pipelines. Retrieval for order status in triage, or no escalation path. And a coding agent allowed to edit and commit without a review gate. Real problems often sit at the boundary of two architectures. Draw on a second pattern only when the two parts of the problem break in different ways that are worth managing separately. If you are reaching for a second pattern because you haven't decided what problem you're solving, that is a deferred decision, not a design. And remember the cost: composing two architectures roughly doubles the surface you maintain, and each one needs its own eval set.

### The output stage
The output stage asks two questions: is this safe to return, and is it the right shape? Output screening judges text before it reaches the user, using a judge model for qualities like policy compliance or a validator for schemas and forbidden fields. Any side-effecting action must pass tool-call authorization before it runs, because output screening judges text, not actions. And outputs that the system isn't confident in need an exception path. In the document pipeline, low-confidence extractions go to a human review queue instead of downstream processing. The pattern to remember from module three is the full guarded path: input screening, model call, output screening, and deterministic authorization before any side effect, with every blocked or failed gate logged.

### The feedback stage
This is the stage most diagrams leave out. A design that ends at response to user cannot notice that it is getting worse. Module two tells you what to log on every request: the request itself, with model version, input tokens and prompt identifier; the response, with output tokens, latency and stop reason; the context, with user role, session ID and whether caching applied; and the outcome, whether the downstream system accepted the output. Module four adds the decision layer on top. Observability collects signals, but a feedback loop maps each signal to a trigger, an owner and an action: signals, triage, decide, act, review. And corrections become data. When a reviewer fixes an extraction, that correction can feed the golden dataset, so the next eval run measures the system against what production actually taught you.

### Reliability belongs in the design too
Module two adds three reliability controls that sit at different layers. Retries with exponential backoff sit close to the API call, for transient errors like 429 rate limits, timeouts and 5xx responses. Circuit breakers sit at the service boundary and trip when a dependency's error rate crosses a threshold, so requests fail fast instead of waiting. Fallback chains sit in the orchestration layer and route to an alternative model tier or a cached response instead of surfacing an error. Put them in the wrong layer and you protect the wrong part of the system. Add model version pinning to every architecture, with a version-update runbook, because an unpinned version can roll forward without re-validation.

### Putting it together
Picture invoice processing. Input: OCR, a tenant ID injected server-side, only the fields the extraction needs. Processing: schema-bound extraction with an evaluator pass. Output: validated JSON, with low-confidence fields routed to a reviewer. Feedback: traces with model version, tokens and stop reason, an acceptance signal from the finance system, reviewer corrections flowing into the golden dataset, and a quality-drift trigger owned by a named person. When an exam scenario describes a system that works but quietly degrades, the missing piece is almost always that last stage.

## Part 1.3 – Select appropriate architectural patterns (workflow, agentic, augmented LLM)
minutes: 11
concepts: Augmented LLM, workflow, agent; predictability and autonomy axes; workflow sub-patterns (chaining, routing, parallelisation, evaluator-optimizer); five deciding factors; prompting before fine-tuning; Skills as packaging; delegation lens
example: A team built an agent for a loan process because the task felt open-ended. At month three, traces showed only four path shapes. A router with four prompt chains would have given clear steps an auditor could inspect.
decision: Choose the simplest pattern that meets the error tolerance and observability requirements; use an agent only when the path truly cannot be enumerated and an unexpected output is acceptable and recoverable.
takeaway: An agent is right only when the steps genuinely can't be written in advance. If you could write them in code, use a workflow and keep the audit trail.
sources: [MODULE 1] Pattern Selection; 90-day retrospective; Try prompting before fine-tuning; Skills-based architecture; Key takeaways · [OFFICIAL ANTHROPIC DOCS] Building effective agents – workflow sub-pattern names (approved gap fill)
narration:
### Three patterns on two axes
Once you know which parts of a task Claude owns, the next decision is structural: what shape does Claude's involvement take? Module one gives three patterns, and places each on two axes. The first axis is predictability, how predictable the path through the work is. The second is model autonomy, how much decision-making you are willing to hand to the model.

The augmented LLM is a single model invocation. You send the request, the model completes the task, and your code handles the wiring. You can add tool use, retrieval or extended thinking to that call, but the model does one bounded job in one pass, and the control flow never branches on what the model decides. It sits in the high-predictability, low-autonomy corner. Use it when the task is well defined, the output is verifiable, and there's no reason to split the work.

A workflow decomposes the task into named steps orchestrated in your own code. Each step may or may not call Claude. Because control flow lives in your code, you can log it, test it and reason about it like any other software. Workflows occupy the middle band: the overall shape is predictable, and each step may involve contained model judgement. Use one when error cost is real, observability matters and the steps can be determined in advance.

An agent gets a goal and a set of tools, and the model decides its own sequence of steps. The control flow lives inside the model. That's what makes it an agent: the path is not written anywhere you can inspect in advance. Use it only when the path cannot be enumerated in advance, and only when an unexpected or inconsistent output is acceptable and recoverable. Claude Code is the production example: it explores an unfamiliar codebase, decides which files to read based on what it found, and runs multi-step work no one could script. In production, agents are bound by constrained tool entry points, per-turn budgets, explicit permissions and stopping criteria. Module one is firm that these constraints are not optional.

### Workflow sub-patterns
Choosing a workflow doesn't fully specify the design. The module notes four workflow shapes; the guide uses Anthropic's names for them: prompt chaining, where steps run in sequence; routing, where an input is classified and sent to a specialised path; parallelisation, where independent pieces run at the same time; and evaluator-optimizer, where one pass generates and another critiques. They aren't mutually exclusive, and most production workflows combine them. The rule is to pick the simplest shape that meets error tolerance and observability requirements, then revisit with production data and escalate only when measurement shows the simpler pattern falling short.

### The five deciding factors
Walk five factors in sequence: predictability, error cost, observability, latency and cost. For each, ask whether it rules out any pattern. The first factor that rules one out is the deciding one, and the tightest constraint decides. When error cost is the binding constraint, error cost picks the pattern. Two cautions from the module. Agents don't automatically cost more than workflows; what drives cost is how much context accumulates and how many model calls are made, so a poorly designed workflow can cost more than a well-designed agent. And workflows and agents fail differently: a workflow fails when a step in your code fails, while an agent fails when the model makes a bad decision somewhere across many turns, which is harder to see and harder to debug. An agent's autonomy is your liability surface, because it can do anything its tools allow, including combinations nobody tested.

### When the team wanted flexibility and got non-determinism
The module's retrospective case has three quotes. One: we picked an agent because we didn't want to constrain it too early, and by month two we'd added so many guardrail tools we'd basically rewritten the workflow inside the agent loop, minus the logging. Two: compliance asked which step approved a disbursement; we pointed at a model turn; they asked which version of the model; the version had rolled forward two weeks earlier and nobody had re-validated. Three: when we mined the traces, the paths fell into only four shapes; we could have written a router and four chains and saved six months.

Read the failures carefully, because the exam does. The team optimised for imagined future flexibility instead of the known present shape. Non-determinism became a compliance problem, because there was no discrete, auditable step to point to. And the unpinned model version was a separate model-governance gap that would have hurt a workflow just as much. Only one of those two compliance failures is about the agent pattern itself. Choosing an agent when you're unsure is not a safe default. If the work had been genuinely unpredictable, the agent would have been the right call for exactly that reason.

### Try prompting before fine-tuning
When prompting feels unreliable, the instinct is fine-tuning. On Claude that's usually the wrong first move. Optimise the prompt, because most reliability problems are prompt problems. Then add tool use or retrieval. Then move to a stronger pattern like evaluator-optimizer. Only then consider fine-tuning, and only for very high volume where inference cost is the real constraint, critical latency where a smaller specialised model wins, or a consistent output format that prompting hasn't solved. Fine-tuning locks you to a model version and narrows your options. The module also notes that fine-tuning Claude is not broadly available, so confirm options with the Anthropic account team before recommending it.

### Packaging and delegation
Alongside the pattern, decide the packaging: a prompt-only solution, direct tool use, or a Skills-based architecture, where a versioned Skill packages the procedure, instructions and scripts as one governed unit. Reach for a Skill when the same procedure runs repeatedly, is distributed across teams or products, or must be versioned and governed. Finally, apply the delegation lens to the pattern itself: does this pattern grant Claude appropriate or excessive decision authority for the risk in front of you? Autonomy is justified only when the stakes and reversibility of the agent's actions support it.

## Part 1.4 – Design multi-agent systems and orchestration strategies
minutes: 10
concepts: Orchestrator and subagents; decomposition, result structure, conflict resolution; fan-out; recoverable vs. unrecoverable failures; coverage check at synthesis; shared trace ID; least-privilege subagent tools; HITL checkpoints

sources: [MODULE 1] Multi-agent systems and orchestration; When fan-out hid a dropped unit · [MODULE 2] Failure modes – orchestrator-workers; Least-privilege tool configuration; Failure taxonomy · [OFFICIAL ANTHROPIC DOCS] Multi-agent research system (approved gap fill)
narration:
### When one agent isn't enough
Pattern selection tells you when to reach for an agent. Some problems are too large or too varied for a single agent to hold in one context. Then the design moves to multiple agents working together. Module one keeps the vocabulary simple: there are two roles.

The orchestrator owns the goal. It decomposes the work, decides what to delegate, and synthesises the results into a single answer. It never does the sub-task work itself; its job is delegation and synthesis. The subagents own scoped sub-tasks. Each runs in its own context, does one piece, and returns a result.

Three things must be designed rather than assumed. How the work is decomposed into sub-tasks. How each subagent's result is structured so the orchestrator can combine it. And how the orchestrator resolves conflicts or gaps when results come back.

### The fan-out pattern
The most common multi-agent shape is a fan-out. A parent agent faces a work item too big for one context: a four-hundred-file codebase to audit, a two-hundred-document corpus to summarise, a regulatory filing to check against fifty rules. The orchestrator splits the item into independent units, dispatches one subagent per unit, in parallel where the units don't depend on each other, and then synthesises the returned results. The win is twofold. Each subagent works in a clean context sized to its unit, and independent units run at the same time.

### Where a failure can be caught
The architectural question to ask is where each failure mode is recoverable. A subagent failure is usually recoverable: the orchestrator can retry the unit, route it elsewhere, or drop it and flag the gap while the rest of the work proceeds. An orchestrator failure usually is not: if the agent that owns the goal and holds the synthesis loses its thread, the whole run fails and partial subagent work may be stranded. So design for the asymmetry. Make subagent work idempotent and retryable, and protect the orchestrator's state.

Module one gives four failure rows to remember. A subagent returns a malformed or empty result: validate each result, retry or re-route the unit, and record the gap rather than failing the run. Two subagents return conflicting results: give the orchestrator an explicit conflict-resolution rule, or escalate the conflict to a human. The orchestrator loses its goal or synthesis state: protect that state and checkpoint progress so a failed run can resume rather than restart. Traces fragment across orchestrator and subagents: propagate a shared trace identifier so one run can be reconstructed end to end. Module two repeats this in its failure-mode table for orchestrator-workers, and adds that attribution later depends on a trace spanning both levels.

### When fan-out hid a dropped unit
Here is the case you must know. A compliance team checked a fifty-section vendor contract against an internal policy checklist. The orchestrator fanned out one subagent per section, each returning pass or flag, and produced a clean summary: forty-eight sections reviewed, three flagged. It went to the legal lead. Two sections had never been reviewed. One subagent timed out and returned nothing. Another failed to parse a scanned page and returned an empty result. The orchestrator counted only what it received.

Three gaps lined up. The count was never reconciled: no rule said results returned must equal units dispatched. A recoverable failure had nothing watching it: a timeout and an empty parse are both the recoverable case, but only if something retries or flags them. And the output read as complete: fluent and well-formed, which is exactly what hid the gap. The fix is a coverage check at synthesis. Results returned must equal units dispatched, or the run flags the difference before anyone reads the summary.

### Trust boundaries between agents
Module two adds least privilege to multi-agent design. Every tool you connect is an attack surface and a cost. In an orchestrator-worker deployment, establish the trust hierarchy by scoping each subagent's tool access to its task, so a subagent can't reach tools its job doesn't need. A summarising subagent has no business holding a write tool.

### Where humans belong
A multi-agent system can take many actions before a human sees anything, so checkpoint placement is a deliberate design choice. A human-in-the-loop checkpoint is a gate that pauses execution for review, positioned by the risk and reversibility of the action about to happen. Place a gate before any irreversible or high-stakes action a subagent would otherwise take on its own. Sample lower-stakes actions instead of gating each one. The gate is part of the orchestration design, not bolted on afterwards.

### Cost and complexity
Multi-agent systems multiply token spend: every subagent has its own context, and the orchestrator pays to synthesise. Reach for the pattern when the work genuinely exceeds one context, not as a default. Each added agent is another failure boundary to observe and govern, so the discipline is the fewest agents that meet the requirement, with clear ownership of the goal. And the dangerous failure is the silent one, a subagent that drops a unit under a confident synthesis.

## Part 1.5 – Apply decomposition techniques for complex problem solving
minutes: 9
concepts: Delegation map; reversibility, stakes, accountability; AI-appropriate, human-retained, collaborative work; capability list; independent units; structured results; boundary conditions; the five-decision assembly

narration:
### Two kinds of decomposition
The word decomposition shows up in two places in the course, and the exam expects you to use both. The first is decomposition by owner: splitting a partner's request into what Claude does, what existing systems do, and what humans do. The second is decomposition by unit of work: splitting a large task into pieces that fit a context, can run independently, and come back in a shape you can combine. Good designs do the first before the second.

### Decomposition by owner: the delegation map
Module one calls the output of owner decomposition a delegation map. For each part of the request you decide not just whether Claude can do it, but whether Claude should own it. Each part lands in one of three categories: AI-appropriate work, human-retained work, or collaborative work where Claude drafts and a person decides. Justify every assignment through three questions. Reversibility: can a wrong call be undone? Stakes: what does a wrong call cost? Accountability: who must answer for it? Delegation is the first of the four AI Fluency competencies the course uses, and this is where you apply it.

The four properties tell you what Claude can be trusted with. Language work, summarising, classification and drafting suit Claude. Authoritative values and arithmetic suit deterministic systems, because next-token prediction is weak on specifics and steerability is weak on precise computation. Live state belongs to the system of record, reached by a tool call. And approvals and exceptions stay with people, because confidence is not validity.

### Decomposition by unit of work
For large tasks, the second decomposition kicks in. Module two's scoping sequence starts it: turn the business requirement into a capability list, naming each capability separately so you can assign it. Then, where a capability is too big for one call, split it into units. Good units are independent, so they can run in parallel without waiting on each other. They are sized to a clean context. And they return a structured result, so the orchestrator or the next step can combine them without guessing. Record the count of units dispatched, because synthesis must reconcile it.

The boundary conditions come out of this step. If a unit is defined as one contract section and some sections are scanned images, that's a constraint. If the design works up to a page count, that's a boundary condition for the statement of work. Decomposition is also where you discover that some capability should never have been Claude's at all.

### A worked decomposition: the law-firm brief
Module one closes with an assembly exercise. A hundred-and-eighty-lawyer firm wants to speed up contract review. Senior associates spend twelve to eighteen hours a week reading thirty-five-page vendor contracts against the firm's playbook. Documents live in iManage, there is a CIO-approved private LLM gateway, and attorney-client privilege rules out consumer-grade tools. The target is sixty percent less associate time per contract, with the senior associate still the final reviewer.

Here's the model answer, decomposed. The entry point is the direct API or SDK in a thin internal web app with the firm's SSO, routed through the approved gateway. The pattern is a parallelised workflow, reviewing the contract section by section, with an evaluator pass enforcing a strict schema on the flagged-clauses output. Claude owns extraction, classification against the playbook, and draft redlines. Existing systems own the rest: the playbook stays a versioned source of truth retrieved per clause at call time, and iManage handles document fetch. Model and context: Sonnet as the default with progressive context, and extended thinking per clause only where an eval justifies it. Humans: the senior associate signs off on every output, and low-confidence clauses are flagged for attention.

Notice what each wrong option in that exercise gets wrong. Each one looks reasonable but fails on a single decision, for example a consumer entry point that privilege rules out, or a design where Claude holds the playbook in its head instead of retrieving the versioned source.

### The cost of getting decomposition wrong
Designs that skip owner decomposition force Claude into work another system would do more cheaply and reliably, or ask it to work without the context a human would have given a colleague. Designs that skip unit decomposition hit the working-memory cliff, or produce one huge call that can't be retried in pieces. Both show up later as cost overruns, unexplained errors or audit findings. Decomposition is cheap at the whiteboard and expensive after launch.

narration:
### Feasible is not the same as worth building
A feasibility verdict tells the business owner the system can be built within budget and constraints. It doesn't say whether building it is worth doing. Business value and ROI mapping answer that second question, and they connect your architecture to outcomes the business already tracks: hours saved, error rates reduced, cycle time shortened, revenue protected. The mapping turns a technical design into a decision a budget holder can defend.

### The five pillars
Module two names five pillars, and the exam guide uses the same list. Efficiency: the same work done faster or cheaper. Transformation: work that wasn't feasible before becoming possible. Productivity: more output from the same people. Solution cost: the run cost of the system itself. And performance SLAs: the service levels the deployment must hold. Map each ROI claim to the pillar it advances, so the value statement says both the number and the kind of value it represents. A claim that sounds like efficiency but is really transformation needs a different baseline, because there was no prior process to compare against.

### Two states and a difference
The mechanism is a comparison between two states. The baseline is how the work is done today, measured in the unit the business cares about. The projected state is how the work is done once Claude is in the workflow, measured in the same unit. Value is the difference between them, minus the cost of running the system. That run cost comes straight from the sizing model you built earlier, so ROI reuses work you already did.

### The four steps
Step one: name the baseline in a business unit. For claims review, that might be analyst hours per claim or average days to resolution. The baseline must come from the business owner's own operational data, because every later number is compared to it. A baseline from intuition produces an ROI figure no finance team will accept.

Step two: predict the post-deployment state in the same unit. If the feasibility verdict needs human review, the projection must include it. Routing low-confidence output to a reviewer reduces labour, but it doesn't eliminate it. Projecting full automation when the design has a review gate overstates the value, and operations will reject the number.

Step three: subtract the run cost from the sizing model. This step isolates recurring run cost only. Build cost is handled in the payback calculation. Reusing the sizing output keeps the analyses consistent, so a change to token budget or model tier updates both the cost ceiling and the value case together.

Step four: state the payback period and the sensitivity. Payback is the time for accumulated gain to cover the build cost and the run cost. Then say how that period moves if volume or gain-per-task assumptions are wrong. Quoting payback without sensitivity invites a decision based on one optimistic scenario.

### The three ROI errors
Module two lists three common errors. The baseline is estimated rather than measured, which stays hidden until finance asks where the number came from, and then the whole case is rebuilt. The projection assumes full automation when the design requires human review, which surfaces in the first operational period when analyst hours don't fall as promised. And the run cost is taken from an average instead of the sizing distribution, which understates cost and overstates value, especially for heavy-tailed workloads where a small fraction of large requests drives most of the spend.

### The outcome document
Module four closes the loop after deployment with the customer outcome document. It has six fields: the use case with its scope boundary, the metric before, the metric after on the same definition, the control that makes the comparison auditable, the measurement owner after the engagement closes, and the reuse potential. Its cautionary case is memorable. An architect wrote the outcome document from what was easy to export: forty thousand requests a month, sub-two-second latency, an error rate under half a percent. The sponsor took it to the CFO, who asked what the deployment had done for the business: what were claim processing times before, and what are they now? The document had no answer. Without the before number there's no story, and without the control the after number is just an assertion. Capture the baseline at the start, so the value case can be proven at the end.
