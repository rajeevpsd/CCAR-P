# Episode 5 – Governance, Safety & Risk Management
intro: Episode five covers governance, safety and risk, fourteen percent of the exam. Five parts: placing guardrails and choosing how they fail, identifying the risks and failure modes of LLM systems, routing decisions to people by stakes, turning compliance obligations into evidenced controls, and building fairness and transparency into the architecture.

## Part 5.1 – Implement guardrails and safety controls
minutes: 12
concepts: Training-time alignment vs. inference-time control; four layers (trained behaviour, system prompt, runtime screening, authorisation); input screening, output screening, tool-call authorisation; model-based vs. deterministic checks chained; indirect injection via retrieved content and tool outputs; refusal stop reason and stop_details; fail open vs. fail closed; Skill supply-chain audit; Claude Code hooks, permissions, sandboxing
example: A support agent with an issue_refund tool had only an output filter. The model called the tool, the refund was issued, and only then did the filter inspect the text and pass it. Input screening, a deterministic authorisation gate before the tool, and output screening, each set to fail closed, would have stopped it.
decision: Place a control at each decision point (input, output, and before every side-effecting tool), use deterministic checks for authorisation and crisp rules, model-based checks for fuzzy intent, and make operator-built guardrails fail closed.
takeaway: One filter at the end isn't a guarded path. Output screening judges text, not actions; a side-effecting tool needs authorisation before it runs.
sources: [MODULE 3] Alignment – what training enforces vs. what you own; layered view; When trained refusals are mistaken for a domain policy; Guardrails – placing screening and authorisation; second injection vector; refusals; fail open vs. fail closed; full guarded path; Skill supply-chain security; When a single output filter looks like a finished design · [MODULE 1] Claude Code governing layers
narration:
### What the model's training covers, and what you own
Before adding controls, module three asks how much safe behaviour is already handled by the model. Anthropic trains Claude against a constitution, a written document describing the values and behaviour the model should show. The module notes the most recent published version is from January 2026. The constitution sets a priority order for when goals conflict: be broadly safe, be ethical, comply with guidelines, and be genuinely helpful. The ordering is holistic rather than strict. The result is that Claude arrives with a broad class of harmful output already reduced, before you write a single prompt.

But that layer is general by design. It doesn't know your partner's domain policy, data-handling rules or authorisation model. A request can fit Claude's general alignment and still violate a deployment rule, such as disclosing another customer's order. Claude can't enforce a rule it was never given. So there are two layers with distinct jobs. Training-time alignment lowers baseline risk. Inference-time control enforces your deployment's rules, through system instructions, input and output checks, tool permissions and human review gates.

### Four layers, each with a blind spot
The module stacks safety in four layers. Trained behaviour covers broad classes of harmful output on every request, but not your domain policy; Anthropic owns it. The system prompt covers role, tone and stated constraints inside a request, but not anything an adversarial input can talk Claude out of, because instructions are not enforcement; you own it. Runtime screening detects disallowed content on input and output, but it doesn't authorise side-effecting actions and can miss novel attacks; you own it. And authorisation decides whether a specific action is permitted for this caller in this context, but it doesn't judge content quality or fairness; you own it too.

The module's postmortem shows the silent failure. A team's internal assistant refused every harmful prompt in testing, so they assumed cross-business-unit disclosure was covered too, and never built an authorisation check. In production, a normal-looking request asked for a forbidden record, and Claude answered it. The rule they believed was enforced didn't exist in any layer.

### Three decision points on the request path
A guarded request path has three decision points. Input screening runs before the model call and decides whether the request should reach the model. Output screening runs before the response reaches the user and decides whether it's safe to return. Tool-call authorisation runs before any side-effecting action, like sending an email, writing to a database or issuing a refund, and decides whether this caller may do this here. They check different things at different points, so a control at one does nothing for the others.

### Model-based or deterministic
At input, use a model-based check when intent is ambiguous, like jailbreak or injection patterns rules can't capture, and a deterministic check when the rule is crisp: a blocklist, a regex, a length or format check. At output, use a judge model for qualities like toxicity or policy compliance, and a validator for known strings, forbidden fields or schema violations. For tool authorisation, almost always deterministic: an allowlist, identity checks and scope validation, because it must be provable and replayable. The two kinds fail differently. A model-based classifier can be evaded by clever phrasing. A deterministic rule is brittle: it blocks exactly what it was written for and misses the rest. So you chain them, knowing what each misses.

### The second injection vector
User-input screening catches instructions the user sends. It doesn't catch instructions embedded in content the system retrieves or receives from tools. In RAG, a malicious instruction in a retrieved document reaches the model after input screening has passed. In an agent, a tool response can carry instructions the model treats as authoritative. The module calls this the dominant injection vector in enterprise deployments with retrieval or tools, and the control is to screen retrieved content and tool outputs before they enter the context, with the same classifier you use on user input.

### Refusals from the API
When Anthropic's streaming classifiers intervene, the Messages API returns stop reason refusal, with a stop details object that the module says is available since Claude Opus 4.7. It carries a policy category and a readable explanation; both are null when the refusal doesn't map to a named category. As of the module's writing the categories include cyber, bio, frontier L L M and reasoning extraction, and it tells you to re-check the list rather than hard-code it. Your application should read the category and route refusal classes differently, tolerate an absent object on models that don't return it, and, once a refusal arrives, reset the context by removing or rephrasing the triggering turn, because continuing on the refused context returns more refusals.

### Fail open or fail closed
A guardrail you build can fail like any dependency: time out, error, become unreachable under load. Then it either passes traffic through unscreened, failing open, or blocks until healthy, failing closed. If you don't choose, the surrounding code usually chooses open. A guardrail that silently passes traffic is worse than one that blocks, because it gives the appearance of protection with none of the function. This applies only to operator-built components; Anthropic's built-in safety controls aren't operator-configurable and don't fail open. The full guarded path, then: user request, input screening set to fail closed, the model call, output screening set to fail closed, deterministic authorisation before any side effect, and every blocked or failed gate logged.

### The single output filter
The module's trace shows why one filter isn't enough. A customer service agent had an issue refund tool. No input screening was configured. The model emitted a tool call to issue a refund, the tool executed with no authorisation gate, and money moved. Only then did the output filter inspect the generated text, find nothing unsafe, and pass it. It sat downstream of the only action on the path that couldn't be undone.

### Skill supply-chain security
Skills are distributable code plus instructions, so they're a supply-chain risk: an untrusted Skill can carry logic that runs commands, reaches the network or touches files the moment it's invoked, invisible to your prompt screening. So audit before trust: read the bundle for anomalous calls such as network requests, shell execution, file access and credential reads, and for out-of-scope behaviour against its stated purpose. A formatting Skill that phones home is out of scope. Then confine it at runtime with least privilege in a sandbox, because a clean Skill can still fetch code at runtime. Allow Skills only from a vetted internal registry, verified publishers and signed releases. Don't assume the platform screens them for you. And record a verdict for every audit: approve, reject, or remediate and re-audit.

### Governing layers in Claude Code
Module one gives the Claude Code equivalents. Hooks are scripts on lifecycle events, used as deterministic gates the agent can't skip. Permission modes control what runs without prompting. And sandboxing contains the workspace with filesystem boundaries, network egress rules and constrained commands, so the environment enforces the boundary, not just the agent's judgement.

## Part 5.2 – Identify risks, limitations, and failure modes of LLM systems
minutes: 8
concepts: Direct prompt injection; indirect prompt injection; token-budget exhaustion; tool and action abuse; data exposure; vulnerability assessment along request and data paths; written risk assessment (category, component, likelihood and impact, mitigation, owner, evidence); four properties as limitations; failure modes by architecture
example: A RAG-backed HR assistant: risks recorded as indirect injection via uploaded policy documents (mitigated by screening retrieved content), data exposure of salary fields in logs (mitigated by server-side redaction), and tool abuse of the leave-booking tool (mitigated by deterministic authorisation), each with an owner and an evidence artifact.
decision: Walk the request and data paths together, at each entry point ask what an adversary could do and which control stands in the way, and record every risk as a written deliverable with an owner and evidence.
takeaway: A risk assessment is a written artifact the security reviewer signs. Every entry point without a control against a plausible attack is a finding.
sources: [MODULE 3] Risks, limitations, and failure modes of LLM systems – risk categories, system vulnerability assessment, documenting the risk assessment · [MODULE 1] Four properties; financial reconciliation case · [MODULE 2] Failure modes by architecture; POC to Prod failure modes · example is illustrative [INFERENCE]
narration:
### From controls to the threats they defend against
Part 5.1 placed the controls. This part asks what they defend against. Module three says an architect is expected to conduct and document a risk assessment for a proposed system as part of a security deliverable, and it gives you the categories to check every design against.

### The five recurring risk categories
Direct prompt injection: a user crafts input that overrides the system's instructions and redirects its behaviour.

Indirect prompt injection: malicious instructions arrive through retrieved content or tool outputs that the model treats as trusted, a vector that user-input screening doesn't catch.

Token-budget exhaustion: oversized or adversarially padded inputs consume the context or output budget, truncating work or inflating cost.

Tool and action abuse: the model is induced to call a side-effecting tool outside policy. That's exactly the failure tool-call authorisation exists to stop.

Data exposure: sensitive fields enter the context window or the logs where they shouldn't, creating a leak independent of model behaviour.

Notice that two of the five, token exhaustion and data exposure, aren't about the model misbehaving at all. They're about what the architecture lets in and what it writes down.

### Where to look: the vulnerability assessment
The module's method is to walk the request path and the data path together. At each entry point, user input, retrieved content, tool outputs, the model's own output, and the logs, ask what an adversary could do there and which control stands in the way. Anywhere there's a plausible attack and no control is a gap. This mirrors the guarded request path: input screening covers user input, content screening covers retrieved and tool content, output screening covers the model's output, authorisation covers actions, and data minimisation and redaction cover the logs.

### Limitations that aren't attacks
Risks also include the model's own limitations, which come from the four properties. Next-token prediction means fluent errors on specifics. Knowledge means stale or confident answers on rare or changing topics. Working memory means truncation at the window edge. Steerability means drift on abstract instructions or precise computation. And non-determinism means the same input can give different outputs, as in the reconciliation case, where a pipeline built as if it were deterministic produced a different categorisation for the same statement in week two and nobody noticed until an analyst re-ran a batch.

### Failure modes by architecture
Module two adds the failure each architecture shows first. Agents: unbounded tool use and growing context, mitigated by per-turn budgets, tool-call limits, stopping criteria and a minimal tool set. RAG: retrieval quality drift, mitigated by keeping retrieval quality in the eval loop and separating live-state queries. Document pipelines: no exception path for low-confidence extractions, mitigated by confidence scoring and a human queue. Orchestrator-workers: blurred failure boundaries, fragmented traces and dropped units at synthesis, mitigated by defined recoverable boundaries, a shared trace ID and coverage reconciliation. And from the POC gap: silent degradation, made-up outputs on edge inputs, or complete failure on an input class nobody tested.

### The risk assessment as a deliverable
The module is explicit that the assessment should be a written artifact. For each identified risk, record the category, the affected component, a likelihood-and-impact judgement, and the mitigating control, with an owner and an evidence artifact. That document is what the security reviewer signs off, and it feeds the compliance control register in part 5.4. A risk with no owner is a risk nobody is watching.

### Exam signals
If a scenario adds retrieval or tool use and asks what new risk appears, think indirect injection and content screening. If it mentions huge pasted inputs or runaway cost from adversarial padding, think token-budget exhaustion, with input limits and budgets. If it describes a model being talked into a refund or deletion, think tool abuse and deterministic authorisation. If sensitive fields appear in logs, think data exposure and redaction before the call. And if the question asks what the architect should produce, the answer is a written risk assessment with owners and evidence, not a verbal assurance.

## Part 5.3 – Apply human-in-the-loop validation strategies
minutes: 9
concepts: Review as a budget; reversibility, cost of a wrong decision, calibrated confidence; routing rule; pre-action approval, post-action audit, sampled review; reviewer view (inputs, output, flag reason); consent fatigue; plan-level review; Diligence; HITL checkpoints in agent workflows
example: Every output went to review with only the output and an approve button. Four hundred items a day turned review into clicking approve. Routing by stakes and showing inputs and the flag reason restored real review.
decision: Route to a person when a decision is low-confidence and either irreversible or high-cost; choose pre-action, post-action or sampled placement by reversibility and volume; and give reviewers the inputs, the output and the reason it was flagged.
takeaway: Route review by stakes, not by volume. Routing everything floods the queue, and a reviewer without inputs and a flag reason can only rubber-stamp.
sources: [MODULE 3] Review routing – what sets the stakes; placement trade-offs; what the reviewer sees; consent fatigue and plan-level review; Diligence; When routing everything to review makes review meaningless · [MODULE 1] HITL checkpoint patterns for agent workflows · [MODULE 2] Low-confidence routing in document pipelines
narration:
### Logging explains; routing prevents
Decision logging gives you a record of what each automated decision was based on. Module three makes the distinction sharp: a log explains decisions after the fact, but it doesn't decide which decisions a person should weigh in on before they take effect. A routing rule stops the wrong ones from taking effect at all. And the log you've already built is the raw material for what the reviewer sees.

### Review is a budget
Think of human review as a budget. You have finite reviewer attention, and you must spend it on the highest-stakes items. Three variables set where it goes. Reversibility: how easily a wrong decision can be undone. The cost of a wrong decision: what the mistake causes if it goes through uncorrected. Those two together set the stakes. A choice that's hard to reverse and expensive when wrong is high stakes regardless of how the system reached it. The third variable is confidence: the system's score for its own output. It doesn't change the stakes. It estimates how likely this output is to be wrong, which tells you how much of the volume should go to a person. And it's useful only if it's calibrated, because a model can be confidently wrong.

### The routing rule
Combine them into one rule. Route decisions to a person when they're low-confidence and either irreversible or high-cost. Let confident, reversible, low-cost decisions through. A confident, easily reversed, cheap decision can usually run without a human. A low-confidence, irreversible, expensive one almost always needs review. When the variables disagree, give more weight to cost and reversibility, because they decide the consequences, and let confidence decide how much of that high-stakes volume can go through unreviewed. And confirm that calibration; it's a task of its own.

### Where the human sits
Once a decision is routed, choose the placement. Earlier is safer and slower. Pre-action approval means the action can't take effect until a person approves it, so nothing irreversible happens unreviewed; but it adds latency to every routed decision and needs reviewer availability, so it doesn't scale to high volume. Post-action audit lets the action run immediately and reviews it afterwards, keeping throughput high; but the wrong action has already happened, so it suits only reversible, lower-cost decisions. Sampled review checks a fraction of decisions to monitor quality without slowing the process; but a bad decision can slip through unsampled, so it monitors the system rather than guarding individual outcomes.

### What the reviewer sees
A reviewer who can't see why an item reached them may approve without the judgement it needed. Give reviewers three things: the inputs that drove the decision, the model's output, and the reason it was flagged. Without the reason, they can't tell an edge case from routine traffic. Without the inputs, they can't tell if the output is right. What you put in front of the reviewer decides whether the review is real.

### Consent fatigue and plan-level review
The module cites Anthropic research on agent autonomy: requiring sign-off on every action adds friction without meaningful safety gain. A better approach is for a person to monitor what's happening and step in when needed. One Anthropic pattern reduces per-step approvals and moves review to higher-value checkpoints, like plan review or exception handling. Consent fatigue is what happens otherwise: asked to approve dozens of times in a row, reviewers start clicking through without reading. That's what led to plan-level review in Claude Code, where a person approves the plan, not each step.

### When routing everything makes review meaningless
The module's transcript is short and memorable. Reviewer: there are four hundred items in my queue today, same as yesterday. Lead: are you reading the inputs on each one? Reviewer: there's no way; I get the output and an approve button; I don't even see the inputs or why this landed with me; after the first hour I just hit approve to keep up. Two independent failures stacked. Volume: oversight that covers everything reviews nothing, so the fix is routing by stakes. Missing context: a reviewer with only an output and a button has nothing to check against, so the fix is showing inputs and the flag reason. Fixing only one still fails.

### Diligence and agent checkpoints
Diligence is the AI Fluency competency behind this: maintaining explicit human accountability checkpoints, noticing when automation pressure is eroding oversight, and auditing workflows for places where AI acts without review. For agents, the routing rule becomes a checkpoint pattern: place a gate before any irreversible or high-stakes action an agent would otherwise take, and sample lower-stakes actions instead of gating each one. Module two's document pipeline is the same idea in a workflow: low-confidence extractions go to a human queue instead of downstream.

narration:
### Constraints eliminate options before preferences do
Module one sets the order. When a partner is subject to attorney-client privilege, HIPAA, GDPR, FedRAMP or an internal data-residency policy, those constraints rule entry points and routes in or out before cost, ergonomics or build effort enter the conversation. Name the governing constraint when you recommend an entry point, and let it eliminate options first. The API or SDK, behind a partner-approved gateway with logging, retention and identity controls in the partner's own infrastructure, is what survives most regulated reviews.

### The constraint table
Attorney-client privilege rules out consumer tiers of Claude dot A I for privileged review, and anything touching privileged material through a surface the firm can't audit end to end. Claude for Work adds admin controls and audit logs, but the firm must still confirm its configuration meets its privilege bar. What survives is the API or SDK behind the firm's application, with SSO, through a firm-approved gateway that logs every request.

HIPAA rules out any route without a Business Associate Agreement for the specific configuration in use. A BAA for one configuration doesn't extend to another, and beta features are generally excluded unless listed as eligible. What survives is the API or SDK on a BAA-covered configuration, via the route the partner already uses. Module two names the HIPAA-eligible paths: the Claude API directly with a signed BAA from Anthropic, AWS Bedrock and Google Vertex AI.

GDPR and data residency rule out routes where the execution region can't be pinned or data leaves the boundary at any step. What survives is a cloud route, Bedrock or Vertex, with the region pinned and DPA terms inherited from the cloud contract. Module two adds that the direct API's inference geo parameter currently supports us and global, not EU pinning. GDPR doesn't itself require EU residency, since cross-border transfers are lawful with a valid mechanism, but where a deployment has an EU residency requirement, use a cloud route. The module says Foundry EU residency was listed as coming in 2026 with no confirmed timeline, so verify before relying on it.

FedRAMP rules out anything not on an authorised environment at the required impact level. The eligible paths are Claude for Government for FedRAMP High civilian workloads, Bedrock GovCloud for FedRAMP High and DoD IL4 and IL5, and Vertex Assured Workloads for FedRAMP High and IL2. Claude Enterprise on the direct API isn't FedRAMP authorised. Authorised government environments lag commercial model releases, so confirm which model the route offers.

An internal residency policy rules out routes outside the approved vendor list, regardless of technical capability. That's procurement, not engineering: the right route is whichever one the CIO already cleared.

### Data handling inside the integration
Module two's PII case shows compliance failing after the route was right. A patient intake summariser sent name, date of birth, social security number, insurance ID, complaint, medications and allergies in the user message. The summary only needed concerns, medications and allergies. Thousands of log entries held social security numbers in plaintext. The fix was a server-side redaction step before the Claude call and a retrieval function supplying only the fields the task needed. Necessity is the filter: if the field isn't required for the language task, it doesn't go in the context window.

### Turning obligations into a control register
Module three takes the next step. Regulations state outcomes, not implementations. Each obligation becomes three things you own: a technical control that achieves the outcome, an owner accountable for it, and an evidence artifact that shows it's live. The evidence artifact is the one most often missed and the one the reviewer checks. Examples from the register: for HIPAA, use only a HIPAA-ready Enterprise plan or first-party API configuration under a signed BAA with HIPAA compliance enabled and only eligible features; evidence is the signed BAA, the admin setting and the eligible-feature list; owner, the security lead. For FedRAMP, an authorised route at the required level; evidence is the authorisation record and confirmation the workload runs only there; owner, the platform owner. For residency, regional processing and storage, with logs, caches, monitoring and retention checked; evidence is the residency configuration and a data-flow record; owner, the data owner. For transparency, decision logging retained and queryable; evidence is a sample reconstruction from the live log; owner, the architect.

### Training use versus retention
Keep two claims apart. Data may be excluded from model training by default while still being retained or monitored for logging, abuse prevention, legal compliance or configured audit purposes. Module two adds that Anthropic doesn't retain API conversation content by default beyond what's technically necessary, but specific carve-outs exist, and your own application logs still capture whatever you send.

### Passing the filter is not finishing compliance
The module's case: a team chose a compliant route for a regulated workload and treated compliance as done. Obligations were mapped to controls once, in a design document, with no owners and no logging to show any control operating. Months later a logging change began writing request metadata to a store in a second region. Nothing caught it, because nobody owned the residency control and no artifact tracked where data landed. The audit asked for evidence that data stayed in-region, and the team had a design document. Configurations drift, so the register is revalidated on a regular cadence.

## Part 5.5 – Address ethical AI considerations (bias, fairness, transparency)
minutes: 9
concepts: Four fairness injection points (retrieval corpus, prompt framing, few-shot examples, downstream routing); three audiences (affected user, regulator, build team); decision logging; fairness-and-transparency checklist; Discernment; subgroup harm hidden by aggregate metrics; decision log as a governed record
example: A team assumed fairness was the model vendor's job. The skew came from their own retrieval corpus, which over-represented some cases, and they had logged too little to reconstruct decisions or rule out the corpus as the cause.
decision: Instrument each injection point, log every decision so it can be explained to users, regulators and your own team, and govern that log as a named control with minimisation, retention limits and access controls.
takeaway: Fairness and explainability are architecture requirements. Unequal outcomes enter at points you control; if you can't reconstruct a decision, you can't explain it.
sources: [MODULE 3] Fairness – injection points; who asks determines what the system explains; decision logging; fairness-and-transparency checklist; Discernment; data handling note; When fairness is treated as the model provider's problem · [MODULE 1] Avoiding bias in prompt construction
narration:
### The failure runtime controls can't see
Runtime controls stop disallowed outputs from leaving the system. Module three points out what they miss: an output that passes every check but produces different outcomes for different people. That's harder to detect and harder to attribute, because on the surface it looks like a normal output.

### Fairness enters at identifiable points
The module's key move is to stop treating fairness as a single property of the model and start treating it as something that enters at specific points you can inspect. In a Claude system there are four. The retrieval corpus can over-represent or under-represent groups, so the context the model sees is already skewed. The framing of the prompt can encode an assumption that pushes outcomes one way. The examples used in few-shot prompting can carry the same skew as the corpus. And the downstream routing, what happens to the output after it's produced, can send some groups down different paths. Each is an injection point you can instrument, which is what makes fairness an architectural property. Module one's prompting guidance covers two of these from the construction side: phrase neutrally and balance examples across the cases the system will see, because bias in a prompt is invisible in any one output and only shows up in aggregate.

### Who asks determines what the system explains
Three audiences need explanations, and each needs a different slice. An affected user needs a clear explanation of why a decision affecting them was made, in terms they can act on; you need to capture the inputs that drove it and the reason. A regulator needs evidence that comparable cases are treated consistently and that a specific decision can be reconstructed on demand; you need a durable, queryable record of inputs, outputs and decision path. Your build team needs enough detail to find why a flagged decision went wrong; you need the full trace: prompt, retrieved context, model output and every routing step.

### Decision logging
To replay and explain one decision, capture the inputs, the retrieved context, the model output and the routing it went through. The module notes this is the same observability instrumentation from production work, pointed at a different question. Instead of asking whether the system is healthy, you're asking why a specific decision happened. The instrumentation is the same; the retention and the query path differ.

### The checklist
The module applies a checklist to a credit-decision support system. Which of the four injection points could skew this outcome, and is each instrumented? For an adverse decision, can you produce the inputs and the reason in terms the applicant can act on? If a regulator asks whether similar applicants were treated comparably, can you query the log and answer? Can your team pull the full trace for any flagged decision? A no anywhere is a design gap.

### Discernment
Discernment, evaluating AI outputs and behaviours, is the competency here. In practice it means judging whether an output is acceptable, needs revision, or needs override, instead of only confirming a value was produced. Applied to fairness, Discernment is what lets a reviewer recognise a skewed or unjustified outcome. A transparency record is what makes that recognition possible.

### When fairness is treated as the vendor's problem
The module's post-incident review is a single quote: we assumed fairness was the model's job; the skew was in our retrieval corpus, and we had logged so little that we couldn't prove it. The model had passed its vendor fairness evaluations. The unequal outcomes came from a corpus that over-represented some cases, an injection point the team never monitored because they'd assigned fairness to the vendor. When outcomes were questioned, there was no decision-level log, so they could neither explain specific decisions nor rule out the corpus, and couldn't answer the one question the regulator asked: where did the skew come from?

### Governing the log itself
The decision log is in scope for the compliance register. In HIPAA or GDPR contexts, logged inputs and retrieved context contain sensitive personal data. Apply minimisation, retention limits and access controls to it, and map it as a named control. Logging for transparency and minimising for compliance aren't in conflict; they need the same log, governed differently. And watch the aggregate trap: an outcome metric can look fine overall while harm concentrates in one subgroup. Measure by subgroup where the decision affects people.

### Exam signals
If a scenario says the model passed the vendor's bias evaluations but outcomes are still unequal, look at the corpus, the prompt framing, the examples and the routing. If a regulator asks for a reconstruction and the team can't produce one, the missing piece is decision logging. If an applicant must be told why they were denied, the system needs the inputs and reason captured in actionable terms.
