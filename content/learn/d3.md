# Episode 3 – Integration
intro: Episode three is Integration, the biggest domain on the exam at nineteen percent. Eight parts: trimming excess tools, closing identity gaps, justifying accuracy and latency trade-offs, monitoring at scale, designing retrieval pipelines, matching retrieval to the data, choosing connection protocols, and progressive versus monolithic context.

## Part 3.1 – Evaluate tool/agent configuration for capability bloat
minutes: 5
concepts: Least privilege; essential vs. convenient tools; trust hierarchy for subagents; removal beats monitoring; deferral is not a permission control
example: A support agent could read tickets, draft replies, issue refunds and delete accounts, but staff only read and draft. Remove the refund and delete tools.
takeaway: If a role doesn't need a capability, remove it. Don't log it, confirm it or instruct around it.
narration:
Every tool you connect to Claude is two things at once: an attack surface and a cost. Capability bloat is when an agent holds more tools or permissions than its task needs.

So audit the tool set the way you'd audit permissions. For each tool, ask: is this essential to the task, or just convenient? If it's out of scope, remove it, and write down why.

The exam loves one particular trap here. A plausible answer adds logging to a dangerous tool, or a confirmation prompt, or a system-prompt rule saying "never use this". Those are compensating controls. The privilege is still there. The strongest answer removes the capability the role doesn't need.

In multi-agent systems, scope each subagent's tools to its own job. A subagent that only reads and reports findings shouldn't inherit the orchestrator's ability to file documents or send notifications. That's the trust hierarchy.

And one subtle point: tool search and deferred loading reduce how much of your context window tool definitions take up. They don't reduce what the agent is allowed to call.
check: Staff only read and draft, but the agent can also delete accounts. Best change? || A) Log deletions || B) Add a confirmation step || C) Remove the delete tool || D) Use a larger model || answer: C || why: Least privilege removes the capability at its source.
check: Do deferred tools reduce an agent's permissions? || A) Yes, deferred tools can no longer be called || B) Yes, but only for tools with side effects || C) Only when the tools are accessed through the API || D) No, they only change what enters context || answer: D || why: A deferred tool can still be found and called.
check: Subagents inherit every orchestrator tool. What's the fix? || A) Scope each subagent's tools to its task || B) Ask subagents to justify any write action || C) Move the shared tools onto an MCP server || D) Upgrade each subagent to a stronger model || answer: A || why: This sets up a trust hierarchy.

## Part 3.2 – Analyze authentication and authorization requirements
minutes: 7
concepts: Server-side identity injection; the Claude layer inherits the existing authorization model; deterministic tool authorization; per-tenant API keys; MCP OAuth 2.1 resource server
example: A legal search tool ran on an all-access service account while the system prompt said "only use permitted documents". The fix: the tool enforces the user's matter-level permissions.
takeaway: Who you are comes from authentication, through the server. What you may do is enforced by deterministic code, never by a prompt.
narration:
Security gaps in Claude integrations usually come from three places.

The first is identity. If a user can type "I'm a regional controller" and unlock data, you have a spoofing gap. Identity and role must come from your authentication layer, and your server injects them into the system prompt. Never trust what the user claims in their message.

The second is authorization. The Claude layer must follow the same access model as the systems underneath it. If your search tool runs on an account that can see every record, a polite instruction in the prompt doesn't help. The tool itself must query as the verified user. And any action with side effects, like booking, refunding or sending, goes through a deterministic check of identity, action and scope.

The third is multi-tenancy. One shared API key means one tenant's spike can trip the limit for everyone, and you can't tell who caused it. Use a separate key per tenant.

For remote MCP servers holding non-public data, the specification treats the server as an OAuth 2.1 resource server. It publishes its metadata, and clients send an access token on every request, instead of sharing a static secret.
check: Users unlock reports by stating their role in chat. What's the gap? || A) The system prompt is too short to list every role || B) The prompt lacks few-shot examples for each role || C) Self-asserted identity instead of server-side injection || D) The model tier is too small to spot false claims || answer: C || why: Identity must come from authentication, injected by the server.
check: Sixty tenants share one API key and a spike degrades everyone. What's the fix? || A) A separate key per tenant || B) Backoff only || C) Batch API || D) Put tenant_id in the prompt || answer: A || why: Per-tenant keys give attribution and isolation.
check: How should a protected remote MCP server authorise clients? || A) With a shared secret stored in each client's config || B) As an OAuth 2.1 resource server with access tokens || C) By VPN restriction alone, with no user-level checks || D) By having each client pass the username in tool calls || answer: B || why: This follows the MCP authorization specification.

## Part 3.3 – Evaluate accuracy-latency trade-offs and justify configuration decisions
minutes: 6
concepts: Tier, thinking, context, retrieval and caching as levers; p95 as the target; binding constraint; one lever at a time; eval as justification
example: Extended thinking on a routing classifier added latency with no accuracy gain. Turning it off and moving that step to Haiku met the SLA.
takeaway: Name the constraint with the least margin and the lever that moves it, and justify the change with an eval.
narration:
Every configuration choice trades accuracy against latency and cost. The levers are model tier, extended thinking, how much context you send, how you retrieve, the output cap, and caching.

Start by stating three numbers that come from the business: the accuracy bar, the latency budget, and the cost ceiling. For latency, design against p95, the time ninety-five percent of requests finish within. The median hides the slow tail, and the slow tail is what breaks SLAs.

Then find the binding constraint, the one with the least margin. If latency is binding, tier and thinking are your strongest levers. If cost is binding, tier and context strategy matter most.

Change one lever at a time, and measure each change against your eval. A common win is per-step tiering: a cheap model for routing, a mid tier for summarising, and the top tier only where the eval says it earns its place.

On retrieval, smaller chunks and hybrid indexes tend to raise quality and latency together. Large dense-only chunks are faster, but they miss exact-match queries like product codes.
check: Users complain about slowness, but median latency looks fine. What should you check? || A) p95 latency || B) Average latency || C) Error rate || D) Token count || answer: A || why: SLA breaches live in the slow tail.
check: Cost is double the ceiling and latency has margin. Which levers matter most? || A) Extended thinking only || B) Tier and context strategy || C) Adding hybrid retrieval || D) Output length on the final step || answer: B || why: These move cost most, validated by eval.
check: What justifies a configuration decision? || A) A successful live demo || B) The team's intuition || C) An eval against the stated thresholds || D) Published vendor benchmark results || answer: C || why: Measured evidence makes a choice defensible.

## Part 3.4 – Analyze observability challenges and select monitoring strategies at scale
minutes: 6
concepts: Silent failure; request, response, context, outcome; tracing, aggregation, anomaly detection, change attribution; per-request decomposition; shared trace ID; audit coverage
example: Dashboards were green while a small share of long documents consumed most of the budget. Breaking cost down by input-length bucket exposed it.
takeaway: LLMs fail quietly. Instrument outcomes, break metrics down per request, and attribute a change before you fix it.
narration:
Traditional systems crash when something goes wrong. LLM systems usually don't. They give an answer that's subtly wrong, with normal latency and no error. So error-rate dashboards alone will miss most problems.

On every request, log four things. The request: model version, input tokens, prompt identifier. The response: output tokens, latency, stop reason. The context: user role, session, whether the cache was hit. And the outcome: did the downstream system accept the result, or was it rejected or corrected?

Then monitor in four layers. Tracing for every request, including tool calls. Aggregation into cost, p50 and p95 latency, task success and error types, broken down per request, because averages hide the expensive tail. Anomaly detection, with alerts on spikes plus periodic comparison for slow drift. And change attribution, which separates model drift, data drift and a model version update, because each one has a different fix.

For multi-agent systems, use one shared trace ID across every agent. And for agents that take actions, check that every action is written to an audit log. An action that isn't logged is one a security reviewer can't approve.
check: Error rate is low, yet escalations are rising. What's missing? || A) A higher error-rate alert threshold || B) Outcome signals and drift comparison || C) Adding p50 latency to the dashboards || D) Verbose logging of raw prompts and PII || answer: B || why: Quality failures don't show up as errors.
check: You can't link subagent failures to their runs. What should you add? || A) Per-agent dashboards || B) Longer timeouts || C) A bigger orchestrator || D) A shared trace ID || answer: D || why: One ID makes the whole run reconstructable.
check: Which three causes does change attribution separate? || A) Model drift, data drift, model update || B) Cost, latency and error rate || C) Prompts, tools and individual users || D) Input size, output size and context || answer: A || why: Each has a different fix.

## Part 3.5 – Design a RAG pipeline with chunking and indexing strategies
minutes: 6
concepts: Fixed, semantic and hierarchical chunking; dense, sparse and hybrid indexing; reciprocal rank fusion; quality vs. latency vs. maintenance; retrieval metrics
example: Policy answers cited an exclusion clause without the heading that limited it to commercial policies. Hierarchical chunking kept section context with each clause.
takeaway: Chunk by the shape of the source, index by the shape of the queries, and measure retrieval on its own.
narration:
A retrieval pipeline makes two key decisions: how you chunk the corpus, and how you index it.

Choose chunking by the structure of the source. Fixed-size chunks with overlap suit uniform, unstructured text. Semantic chunking splits on meaning, so each chunk can stand on its own. Hierarchical chunking keeps sections and subsections together. That's what you want for contracts, manuals and policies, where a heading changes what a clause means.

Choose indexing by how people ask. Dense embeddings match meaning, which is great for paraphrased questions. Sparse keyword search, like BM25, matches exact tokens: part numbers, error codes, statute citations. Most production systems see both kinds of query, so hybrid is the common answer. Merge the two ranked lists with reciprocal rank fusion, a low-tuning default.

Every choice trades retrieval quality against latency and maintenance. And retrieval quality doesn't show in the output. A confident answer built on the wrong chunk looks exactly like a right one. So measure retrieval precision and recall against a labelled set, and keep measuring as the corpus grows.
check: Users search by part number and by description. Which index fits? || A) Dense embeddings only || B) Sparse keyword search only || C) Hybrid with reciprocal rank fusion || D) No index, just a long prompt || answer: C || why: Mixed query patterns call for hybrid.
check: Clauses lose the context of their section heading. Which chunking fits? || A) Hierarchical || B) Smaller fixed chunks || C) Larger top-k || D) A bigger embedding model || answer: A || why: Preserve document structure.
check: Answers turn confidently wrong after a document refresh. Where do you look first? || A) Silently changed model weights || B) A temperature that is set too low || C) A context window that has shrunk || D) Retrieval and indexing || answer: D || why: For example, mismatched embeddings or a broken re-index.

## Part 3.6 – Apply retrieval strategies matched to data shape and query pattern
minutes: 5
concepts: Stable knowledge vs. live state; tool calls for systems of record; similarity is not truth; monolithic prefix for small stable content; synthesis across documents
example: "Where's my order?" returned two stale chunks and a confident wrong answer, while an order-status API sat unused.
takeaway: If it was true yesterday and will be true tomorrow, retrieve it. If its value changes on its own, call the system that owns it.
narration:
Here's the most common reference-architecture mistake: using retrieval where a tool call belongs.

Retrieval is built for stable knowledge: FAQs, manuals, policies, things that stay true between index refreshes. Live state is different. Order status, inventory and account balances are owned by a system of record and change independently. If you index snapshots of live state, the retriever returns whichever stale snapshot looks most similar, and the model answers confidently. No error, normal latency, wrong answer.

A shorter refresh interval won't fix this, and neither will a higher similarity threshold or a better embedding model. Similarity isn't truth. The fix is a tool call to the system that owns the data.

So classify each kind of data. Stable reference content goes through retrieval, or a cached prefix if it's small and always needed. Live state comes from the system of record. Precise numbers come from deterministic computation.

And when a question needs synthesis across many documents, top-k chunks often miss the pattern. Break it into per-document extraction, then synthesise over the structured findings.
check: Answers about order status contradict the database. What's the fix? || A) An hourly refresh || B) Call the order-status API || C) A higher similarity threshold || D) Better embeddings || answer: B || why: Live state belongs to the system of record.
check: Where should a small, stable policy needed on every call go? || A) A cached monolithic prefix || B) A vector index refreshed daily || C) Fine-tuning on the policy || D) A tool call on every request || answer: A || why: There's no need to pay retrieval overhead for it.
check: Cross-document synthesis keeps missing patterns. What should you do? || A) Raise top-k to fifty and let the model synthesise || B) Switch to sparse-only retrieval for exact matches || C) Answer the synthesis from the model's own memory || D) Extract per document, then synthesise || answer: D || why: Retrieval scores chunks independently, so synthesis needs structure.

## Part 3.7 – Evaluate connection protocols and select the integration mechanism
minutes: 7
concepts: API vs. SDK; MCP for sharing across clients; MCP vs. tool use; Agent SDK for embedded loops; Claude Code for developers; agent-to-agent (source gap)
example: A bank proposed Claude Code on branch laptops with MCP servers. The better design was a custom web app on the API with SSO, deterministic compliance code and server-side audit.
takeaway: The entry point follows the user and the work. Use MCP only when two or more clients reuse the same tools.
narration:
Choosing how Claude connects is about matching the mechanism to the job.

The direct API is the foundation layer, giving you full control and full responsibility. The SDKs offer the same capability in language-native code, and they're the default for embedding Claude in a product.

MCP is a protocol for sharing tools across clients. Build a server once, and Claude.ai, Claude Code and your internal app can all use it. If only one product will ever use those tools, MCP just adds overhead. MCP and tool use aren't really alternatives, either. MCP servers expose tools that clients call through tool use.

The Agent SDK runs a managed agent loop, the same one behind Claude Code, inside your own application. Pick it when Claude needs to act across several turns in your product and you don't want to build the loop yourself.

Claude Code itself is for developers doing engineering work. It isn't a backend for operational staff or multi-tenant products.

Agent-to-agent protocols cover delegating to agents you don't own, possibly on other frameworks. Anthropic's documentation doesn't address them directly, so treat this as an inferred principle.
check: Claude.ai, Claude Code and an internal app all need the same Jira tools. Which mechanism? || A) Separate integrations || B) Claude Code backend || C) A static prompt || D) One MCP server || answer: D || why: MCP shares one tool surface across clients.
check: An agent embedded in your web app must act over several turns. Which interface? || A) Agent SDK || B) Claude Code CLI || C) A single SDK call || D) MCP as the loop || answer: A || why: The Agent SDK provides the managed loop.
check: Branch staff need an operations assistant. Which entry point is wrong? || A) A custom web app on the API behind SSO || B) Claude Code on their laptops || C) An SDK-based app integrated with SSO || D) An internal portal || answer: B || why: Claude Code is for developers, not operational staff.

## Part 3.8 – Evaluate progressive discovery vs. monolithic context strategy
minutes: 6
concepts: Monolithic, progressive, retrieval, compaction; combining strategies; tool search with defer_loading; Skills progressive disclosure; strategy vs. sizing
example: An agent with 12 MCP servers and 350 tools deferred the long tail with tool search and kept its five hottest tools loaded, freeing context before any work began.
takeaway: Load what's needed at the start, carry forward what's recent, fetch the rest on demand, and compress what's old.
narration:
A context strategy decides how information reaches the model on each call. It sits on a spectrum.

Monolithic means loading everything at once. It suits bounded tasks with stable, cacheable prefixes. But in long conversations or agent loops, context piles up turn after turn, cost grows, and eventually you hit the window's edge.

Progressive means carrying forward only what the next step needs. It's the right default for most production work.

Two more strategies sit in between. Retrieval fetches knowledge just in time. Compaction summarises older material so long sessions can keep going, but it can drop exact identifiers and numbers, so preserve those.

Real systems combine all four. A coding agent loads a small stable prefix, carries recent tool results forward, retrieves files when it needs them, and compacts early exploration.

Progressive discovery applies to tools and Skills as well. With the tool search tool, you mark rarely used tools as deferred, and Claude loads them only when it finds it needs them. You still send every definition, and you keep your three to five most-used tools loaded. Skills work the same way: metadata first, full content on demand.

check: Which tools should stay non-deferred? || A) The most frequently used few || B) None || C) The tool search tool should be deferred || D) Every side-effecting tool || answer: A || why: This avoids a search step on most turns.
