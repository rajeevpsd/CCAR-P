## Part 3.1 – Evaluate tool/agent configuration for capability bloat
minutes: 9

sources: [MODULE 2] Least-privilege tool configuration · [MODULE 1] Pattern Selection – agent risk callout; Reference architectures – agent failure mode · [MODULE 3] Tool and action abuse · [OFFICIAL ANTHROPIC DOCS] Tool search tool (approved gap fill) · example is illustrative [INFERENCE]
narration:
### What capability bloat means
Capability bloat is what happens when an agent or tool-using system accumulates more tools and permissions than its job needs. It creeps in naturally. A team adds a tool for one edge case, another because it was easy to connect, a third because a previous project had it. Each addition looks harmless. Together they widen what the system can do, including combinations nobody tested.

Module one frames the risk precisely: an agent's autonomy is your liability surface. An agent can do anything its tools allow. The broader the tool permissions, the larger the space of things that can go wrong. Keep the tool entry point as narrow as the task allows. The reference-architecture table names the agent's characteristic failure the same way: unbounded autonomy, meaning state-changing tools with no human review, no turn limit, and no way to measure whether the goal was met.

### Least-privilege tool configuration
Module two turns this into an audit procedure. Every tool you connect to a Claude system is both an attack surface and a cost. Audit the tool set the same way you audit permissions. For each connected tool, ask whether it is essential to the task or merely convenient. Remove the ones that are out of scope, and record the justification for each removal. That last step matters, because it stops the tool from quietly returning, and it gives a reviewer the reasoning.

In an orchestrator-worker deployment, establish a trust hierarchy. Scope each subagent's tool access to its task, so a subagent can't reach tools its job doesn't require. A research subagent that reads documents doesn't need a send-email tool. A code-review subagent in Claude Code runs with read-only tools.

### Why bloat costs money and accuracy
Bloat isn't only a security issue. Module two calls every tool a cost as well as an attack surface, and tool definitions occupy context, so every extra tool adds tokens to every call. And from module two's failure-mode table, an agent that can call tools without budget constraints or turn limits runs up cost and latency in ways that stay invisible until one request exceeds the budget ceiling. The mitigations there apply directly: per-turn token budgets, a maximum number of tool calls, explicit stopping criteria, a tool set constrained to the minimum, and evals of the agent's stopping behaviour, not just its output.

### Tool and action abuse
Module three names the security version of bloat as a risk category: tool and action abuse, where the model is induced to call a side-effecting tool outside policy. The control that exists to stop it is tool-call authorisation, a deterministic allowlist plus identity and scope checks before any side effect. But authorisation works best on a small, deliberate tool set. The fewer side-effecting tools exist, the fewer places an injected instruction can do harm.

### When you genuinely need many tools
Sometimes a system legitimately needs a large catalogue, for example an assistant that spans many internal services. The training modules don't cover this case, so the guide fills it from Anthropic's documentation on the tool search tool. You mark tools as deferred, and Claude searches the catalogue and loads only what it needs for the current task. Two points matter for design. You still send the full tool definitions; deferred loading controls what enters the context window, not what you send. And the docs advise keeping the three to five most frequently used tools loaded up front, and never deferring the search tool itself. Deferred loading is a context-efficiency tool. It doesn't replace least privilege, because a deferred tool is still a tool the model can reach.

### How the exam frames it
Expect a scenario where an agent has drifted into holding many tools and something went wrong, or where a design review is asked to tighten a configuration. The right answer removes out-of-scope tools with a recorded reason, scopes subagents, adds budgets and stopping criteria, and puts authorisation before side effects. The weaker answers sound plausible: add a stronger system prompt telling the model not to misuse tools, add output filtering, or move to a more capable model. None of those shrink the surface.

## Part 3.2 – Analyze authentication and authorization requirements to identify security gaps
minutes: 10
concepts: Server-side identity injection; identity in the user message is manipulable; authorisation model of underlying systems governs the Claude layer; tool-call authorisation is deterministic; gateway holding the API key; per-tenant API keys; constraint-to-integration matrix; minimum necessary context
example: A multi-tenant SaaS support agent passed the tenant ID in the user message, shared one API key across tenants, and let the model call a refund tool directly. The fix: inject tenant and role server-side, issue per-tenant keys, and put a deterministic allowlist with identity and scope checks before the refund tool.
decision: Verify identity on the server before the Claude call, inject role and permitted scope into the system prompt, reuse the existing authorisation model for every tool, and make side-effect authorisation deterministic.
takeaway: A user can't be allowed to assert their own role. Identity comes from your authentication layer, and authorisation is enforced in code, not in the prompt.
sources: [MODULE 2] Integration – identity and SSO, authorisation and policy layers; Identity and authorisation – where verification happens; Constraint-to-integration matrix; multi-tenant API key risk; Critique the integration diagram · [MODULE 3] Tool-call authorisation; Authorization layer · [OFFICIAL ANTHROPIC DOCS] MCP authorization specification (approved gap fill) · example is illustrative [INFERENCE]
narration:
### Where verification happens
Module two is direct about this. Identity verification belongs on the server, before the Claude call. The user's identity and role are injected into the system prompt by your server, not provided by the user in their message. The reasoning is simple. Anything the user includes in a message is under their control and can be manipulated. If the system lets a user assert a role, for example, as a senior manager, show me the regional figures, that claim is unverified and can be faked. Identity must come from your authentication layer, not from user input.

When you pass user context into the prompt, include the user's role and what data they're authorised to access. Add extra context, such as department, permission level or account identifiers, only when it's needed to shape Claude's response. Don't include it by default, because everything in the context window travels with the request and lands in your request logs.

### Identity and authorisation are two separate layers
The module lists these as distinct integration layers. The identity layer asks where the user identity boundary sits relative to the Claude integration point, who the user is in the context of a Claude call, and how that identity gets into the prompt safely. What breaks when it's wrong: Claude can't scope its responses to what that user may see, and identity passed as a raw field in the user message is manipulable. Server-side injection removes that risk.

The authorisation layer asks which capabilities this user or role has, and what data they can access. The authorisation model that governs your existing systems needs to govern the Claude layer as well. What breaks when it's wrong: a Claude integration that bypasses the underlying system's authorisation gives users access to data they aren't allowed to see, through a path that was never designed to enforce the policy. This is the classic gap the exam asks you to find. The assistant can query a database with a service account that sees everything, so anyone who can talk to the assistant can see everything.

### Authorisation for actions must be deterministic
Module three adds the action side. Tool-call authorisation runs before any side-effecting action, such as sending an email, writing to a database or issuing a refund, and determines whether this caller may perform this action in this context. The module is clear that authorisation should almost always be deterministic: an allowlist of permitted actions, identity checks and scope validation. A model-based check is rarely appropriate here, because authorisation must be a decision you can prove and replay. It's also the safety layer that covers what screening can't: screening detects disallowed content, but it doesn't authorise actions.

### Patterns from the constraint matrix
Module two's constraint-to-integration matrix shows how identity works under real constraints. For attorney-client privilege, the API runs behind the firm's own application, through a firm-approved gateway that holds the API key, enforces who can access what, and produces an audit log the firm owns. Users sign in through SSO, and identity and permissions are assigned by the server and can't be claimed by the user. For HIPAA, users are verified through the partner's authentication system and access to protected health information is limited to the minimum necessary. For FedRAMP, users authenticate through the agency's approved identity provider and access is controlled by the agency's role and policy layer. For internal data-residency policy, users sign in through the partner's standard SSO with roles from existing policy. The common thread: the Claude layer inherits the enterprise's identity and authorisation, it doesn't invent a new one.

### Multi-tenant isolation
One more gap the exam likes. Module two warns that a multi-tenant system running on a shared API key can't attribute a rate-limit breach to the tenant that caused it. When the organisation-level limit trips at peak, the spike is visible but the source isn't, and every tenant absorbs the impact. Separate API keys per tenant are required for attribution and isolation in any production multi-tenant deployment. Pair that with server-injected tenant identity, so one tenant's data can't be requested by another.

### MCP authorisation
When tools are exposed over MCP, the same principle applies at the server boundary. The modules don't cover MCP's authorisation mechanics, so the guide fills that gap from the MCP authorisation specification. The architectural point is that an MCP server is a boundary where the caller's identity must be checked and its scope enforced. Don't assume a connector is safe because the client in front of it is authenticated.

### Reading a diagram for gaps
When a scenario shows an integration diagram, walk it in order. Where does identity come from: the server, or the message? Does the Claude path enforce the same authorisation as the underlying system, or does it use a broad service account? Is there a deterministic authorisation check before each side-effecting tool? Is there one API key shared across tenants? What sensitive fields enter the context window that the task doesn't need? Each yes in the wrong place is a gap, and the fix is almost always to move the control to the server side, into code.

## Part 3.3 – Evaluate accuracy-latency trade-offs and justify configuration decisions
minutes: 9
concepts: Levers: model tier, extended thinking, context strategy and size, retrieval, output length cap, caching; p95 as the design target; cost and latency budgets both binding; the load-bearing control; per-step routing; calculators
example: Defaulting to the best model with thinking on everywhere caused a 7× cost overrun and 2.3 s median latency against an 800 ms target, with no CSAT gain. Routing the classifier to Haiku with thinking off, summarisation to Sonnet, and keeping Opus on composition cut cost 71% and brought median latency to 940 ms.
decision: Identify which budget, cost or latency, has the least margin, name the control that most moves it, and justify the configuration by that load-bearing control, with each step's tier confirmed by an eval.
takeaway: Find the binding constraint and the lever that moves it. Naming that lever is what makes a configuration defensible rather than lucky.
sources: [MODULE 1] Model & Context Strategy; extended thinking; When defaulting to Opus everywhere produced a 7× cost overrun; Cost & latency calculator and model answer · [MODULE 2] POC to Prod – cost, latency, p95, caching; Cost & reliability calculator scenario; max_tokens cap
narration:
### The levers
Every configuration choice trades accuracy against latency and cost. Across modules one and two, the levers are the same handful. The model tier. Extended thinking, on or off. The context strategy and how much context you send, since cost and latency grow linearly with input length. How you retrieve. The output length cap, set with max tokens. And prompt caching, which cuts both cost and latency when a long, stable prefix is reused. The architect's job isn't to know every lever's exact value. It's to know which lever moves which budget.

### Latency is a distribution
Module two insists on the right latency metric. A demo usually runs one request at a time, and median latency under a single request is a different number from p95 under concurrent load. P95 is the latency below which ninety-five percent of requests complete; only the slowest five percent fall above it. SLA breaches and user abandonment come from that slow tail, so p95 is the more useful design target than the median. The same is true of cost: token distributions are skewed, and a model built on the average can underestimate cost by a factor of two or three.

### Two budgets, both binding
Module one's calculator sets the exercise. You pick a model tier, a context strategy, a daily call volume and extended thinking on or off, and you have to meet a cost ceiling and a latency budget at the same time. The two can't be traded against each other. Module two's calculator gives a concrete scenario: a customer service agent with fifty thousand requests a month, a five-thousand-token stable system prompt, three hundred tokens of input, four hundred of output, an eight-hundred-dollar monthly ceiling and a three-second p95 target. More than one valid configuration exists.

The model answer is the rule to remember. The dominant constraint depends on which budget is tighter. If latency is binding, the model tier and extended thinking are the load-bearing controls, because they most directly move latency. If cost is binding, the tier and the context strategy are load-bearing. The load-bearing control is the one tied to whichever budget has the least margin, and naming it explicitly is what makes the configuration defensible rather than lucky. In the module two scenario, a large stable system prompt also points straight at caching, and a max tokens cap protects both budgets from the long-output tail.

### The case that ties it together
Revisit the case from episode two through this lens. Ninety days after launch, cost was seven times the model and median latency was 2.3 seconds against an 800-millisecond target, with no satisfaction gain. Three things compounded: no model-tier decision existed at any step, so the default carried to deployment; cost was reviewed monthly, so the gap surfaced late; and extended thinking was on for a routing classifier that needed no reasoning. Here both budgets were blown, and the levers were tier and thinking. The team built an eval set per step, routed the classifier to Haiku, summarisation to Sonnet, and kept Opus only for final composition. Cost fell seventy-one percent, median latency reached 940 milliseconds, and satisfaction stayed flat, which proved the expensive configuration had bought nothing.

### Extended thinking as a latency lever
Extended thinking is the lever most often misused. Thinking tokens are billed as output and add latency on every call where thinking engages. Module one's rule is to run evals without it, work on the prompt, and enable it only for a measured accuracy gap. A routing classifier is the textbook case where it adds latency with no accuracy gain.

### Justifying the decision
When you present a configuration, say three things. Which budget is binding, and how much margin each has. Which control you moved, and why that control moves that budget. And what the eval showed per step, so nobody can say you traded accuracy away blindly. A configuration justified that way survives a design review. One justified as we picked the best model doesn't.

### Common traps
Expect distractors that move the wrong lever. Adding hybrid retrieval when the problem is latency from thinking. Upgrading the tier when cost is binding. Removing thinking everywhere when only one step needed it, which can drop accuracy where the eval showed thinking earned its place. And optimising the median when the SLA is defined at p95.

## Part 3.4 – Analyze observability challenges and select monitoring strategies at scale
minutes: 9
concepts: Silent wrongness; four things to log (request, response, context, outcome); request-level tracing; metric aggregation; per-request decomposition; anomaly detection; change attribution (model drift, data drift, model update); shared trace ID across agents; audit coverage of agentic actions
example: Dashboards looked healthy while 3% of requests consumed most of the budget and produced wrong outputs. Per-request decomposition exposed the tail, and change attribution showed data drift from a new input type, not a model change.
decision: Instrument request-level traces at design time, aggregate them into the metrics the deployment needs, alert on thresholds and distribution shifts, and design attribution so model drift, data drift and model updates can be told apart.
takeaway: An LLM system doesn't crash; it quietly gets answers wrong. Aggregate metrics catch obvious failures; per-request decomposition catches the rest.
sources: [MODULE 2] Integration – observability and audit logging; Observability: what to log, what to trace, and why; A/B & Obs – observability at scale, change attribution; cost and risk callouts · [MODULE 1] Multi-agent failure table – shared trace identifier · example is illustrative [INFERENCE]
narration:
### Why LLM observability is different
Module two opens with the core problem. An LLM-based system is harder to debug than traditional software because it doesn't crash when something goes wrong. It produces a subtly wrong response. Standard logging catches errors and timeouts. It doesn't catch an answer that's quietly incorrect in a way that has real business consequences. So observability for Claude has to be designed for silent wrongness, not just for outages.

### What to log on every request
The module names four things. The request: model version, input token count and prompt identifier. The response: output token count, latency and stop reason. The context: user role, session ID, and whether caching was applied. And the outcome: whether the downstream system accepted the output, and any rejection signals. That last one is the closest you get to ground truth in production. An acceptance signal from the system consuming the output tells you, at scale, whether outputs are being used.

### Four questions, four layers
Observability at scale has to answer four questions: what is the system doing, how well is it performing, when did it change, and why did it change? Each needs its own layer.

Request-level tracing is the raw material. Every request produces a trace with the model, model version, input and output tokens, latency, stop reason and any tool calls.

Metric aggregation turns traces into dashboard metrics: cost per request, latency p50 and p95, task success rate where the downstream system gives an acceptance signal, and error rate by error type. The critical warning is that aggregate metrics can look healthy while a small fraction of requests consumes most of the budget. Per-request decomposition is what protects you.

Anomaly detection sets threshold alerts on the metrics that matter. The module's examples: a cost spike above one hundred and fifty percent of the seven-day average deserves an alert, and so does p95 latency crossing the SLA. Model drift, a gradual change in the distribution of outputs over time, is harder to catch with thresholds and benefits from periodic distribution comparison.

Change attribution is the hardest layer. When a metric moves, the instrumentation should distinguish three causes. Model drift: the model's behaviour on stable inputs changed. Data drift: the input distribution changed. And model update effects: the model version changed and behaves differently on existing inputs. They have different fixes, and mixing them up produces the wrong one. You can only attribute a change if you logged the model version and can compare inputs over time.

### Observability across agents
In multi-agent systems, traces fragment across the orchestrator and its subagents. Module one's fix is a shared trace identifier propagated through every agent, so one run can be reconstructed end to end. Without it, you can't tell a recoverable subagent failure from an unrecoverable orchestrator one.

### Observability as the price of autonomy
Module two makes a point that matters for agent designs. Security organisations increasingly treat observability as the precondition for enabling agents at all. Without a trustworthy audit trail, an autonomous system isn't approved to act. Design for that standard. As a design-review item, verify which agentic actions are actually recorded in audit logs across your chosen surfaces, because coverage varies by surface, and an action that's taken but not logged is, to a security reviewer, an action that can't be allowed.

### Build it before the incident
Both cost callouts in module two say the same thing. Instrumentation added after the first production incident means the root-cause question can't be answered from the data you have. Building it correctly the first time is cheaper than reconstructing logs afterwards. And the risk callout: a system with aggregate-only metrics can look healthy while a small fraction of requests is consuming most of the budget and producing wrong outputs.

### Selecting a strategy
When an exam scenario asks you to choose a monitoring strategy, match the layer to the symptom. Can't explain a cost spike? You need per-request decomposition. Quality slid with no code change? You need distribution comparison and change attribution, with model version in every trace. A multi-agent run went wrong and nobody can say where? You need a shared trace ID. Security won't approve an agent? You need audit coverage of every agentic action. And in all cases, connect the technical metrics to the business metrics the sponsor tracks, which you'll see again in episode four.

## Part 3.5 – Design a RAG pipeline with appropriate chunking and indexing strategies
minutes: 9

sources: [MODULE 1] RAG Pipeline Design – chunking table, indexing table, reciprocal rank fusion, trade-off; Reference architectures – RAG · [MODULE 2] Failure modes by architecture – RAG retrieval drift; [EXAM GUIDE] Sample question 3 context · example is illustrative [INFERENCE]
narration:
### What a RAG pipeline is
Module one describes retrieval-augmented generation done well: a stable knowledge corpus, such as product manuals, internal docs or regulatory text, is chunked and indexed. When a question arrives, the most relevant chunks are retrieved and passed to the model as context. This part goes one level deeper into the pipeline: how the corpus is broken into chunks, how those chunks are indexed, and how the retrieval strategy is matched to the queries the system will see.

### Chunking: by what the corpus is
A chunk is the unit that gets retrieved. The module's rule is that the chunking approach is chosen by the structure of the source, not by a default size. There are three approaches.

Fixed-size chunking splits text into uniform spans, with overlap, regardless of structure. It earns its place on homogeneous, unstructured text where natural boundaries are weak, and it's the simplest to operate.

Semantic chunking splits on meaning boundaries: topic shifts and sentence groups that hang together. It fits prose where a retrieved chunk must be self-contained to answer well, and it reduces cuts in the middle of an idea.

Hierarchical chunking preserves document structure, sections and subsections, and retrieves at the level that fits. It fits structured documents like contracts, manuals and policies, where section context carries meaning. A clause pulled out of its section can mean something different.

### Indexing: by how queries are phrased
Indexing decides what similar means when a query arrives, and the strategy is chosen by the query pattern.

Dense indexing, with embeddings, matches semantic similarity, meaning rather than words. It suits queries phrased differently from the source: paraphrase, intent and concept matching.

Sparse indexing, keyword-based, for example BM25, matches exact terms: identifiers, codes and names. It suits queries that hinge on specific tokens, such as part numbers, statute citations or error codes.

Hybrid indexing uses both and combines the results. It's the common production case for mixed query patterns, and it recovers the exact-match results dense retrieval misses. When a hybrid index returns two ranked lists, they must be merged. Reciprocal rank fusion is the standard, low-tuning way to do it: each result is scored by its rank in each list, and the combined score favours items that rank well in both. The point for an architect is that combining dense and sparse results is a design decision with a known, defensible default.

### The trade-off you must state
Every retrieval design trades three things. Retrieval quality: does the right chunk come back? Latency: how long does retrieval add to each request? And maintenance: how much does the pipeline cost to keep correct as the corpus grows and changes? Smaller chunks and hybrid indexing tend to raise quality and latency together. Larger chunks and dense-only indexing lower latency and maintenance but miss exact-match queries. There's no universally right point, only the point that fits this corpus and these queries, stated as a trade-off you can defend. The cost callout adds: size the pipeline to the query patterns you actually have, not to the most thorough design imaginable.

### How RAG pipelines fail
Module two's failure table names the first thing that breaks in RAG: retrieval quality drift. It happens when documents are added or removed without reindexing, when query and document representations fall out of alignment, or when the index refresh schedule creates staleness for queries about live state. The mitigations: keep retrieval quality in the eval loop, monitor retrieval precision and recall as system metrics, not just output quality, and separate live-state queries from static knowledge queries. Module one's limits on retrieval add three more failure modes: synthesis across many documents the retriever scores independently, chunking that splits semantic units like tables, code or multi-paragraph arguments, and recall failures where the correct document never enters the top results.

### Measure what you can't see
The risk callout is the line to remember. The failure mode is a confident answer built on the wrong chunk. Retrieval quality isn't visible in the output; it has to be measured against a labelled set. That's why RAG design ties straight into evaluation: a labelled set of queries with the chunks that should come back, scored on every change to chunking, embeddings or index configuration. And complexity grows over time. A pipeline that was correct at launch can degrade silently as documents are added, so every chunking and indexing choice is something you'll maintain.

### Exam signals
If a scenario mentions part numbers, error codes or citations being missed, think sparse or hybrid. If it mentions answers that miss section context in contracts or policies, think hierarchical chunking. If it mentions quality sliding as the corpus grew, think retrieval drift and reindexing, monitored as a metric. And if the question is about current values like order status, it isn't a RAG pipeline problem at all, which is the next part.

## Part 3.6 – Apply retrieval strategies matched to data shape and query pattern

narration:
### The skill underneath: context engineering
Module one names the broader skill here as context engineering: deciding which mechanism is responsible for getting each kind of data in front of the model. Retrieval over a vector index is one mechanism. A tool call is another. Information placed directly in the prompt is a third. And application-managed memory is a fourth. Each fits a different shape of data. The most common reference-architecture mistake in the whole course is using retrieval where a tool call belongs.

### The retailer trace
Here's the trace the module uses. An electronics retailer's assistant gets, where's my order? Retrieval returns two chunks. The first, with a similarity of 0.78, says the order was placed on the eleventh of June and shipped on the twelfth by standard courier, with a tracking number. The second, at 0.74, says the order is being processed, with dispatch expected within twenty-four hours. The model answers: your order shipped on the twelfth of June.

Both chunks were real strings that existed in the corpus at different times. The index conflated them. In reality the order had shipped, been returned to the depot because of a damaged label, and was waiting for re-dispatch. That current state appeared in neither chunk, because an index captures what was true when it was written, not what is true now. And a customer service tool to fetch live order status existed in the partner's API. It wasn't called.

### What broke, and why
The module breaks it into four lessons. First, a category error. Retrieval is the right mechanism for knowledge: FAQs, policies, manuals. It's the wrong mechanism for transactional state. Second, it's a data-architecture failure, not a retrieval failure. Live state had been represented as historical text snapshots, so the system searched past snapshots instead of querying the system of record. Third, similarity is not truth. A higher similarity score means the text was semantically close to the query, not that it's current. Fourth, the fix is a tool call. Not a better chunker, not a shorter refresh interval, not a higher similarity threshold. The knowledge base keeps the FAQ content. The transactional database keeps the orders. Two kinds of data, two access patterns, two mechanisms.

### How to recognise it
The symptoms are distinctive: stale chunks, results that shift with each index refresh, and answers that contradict the database. A better embedding model or more frequent refresh won't fix it. And the risk callout explains why it's dangerous: the system looks healthy. Normal latency, no errors. There's no signal that anything is wrong until a user notices the answer doesn't match reality. The model returned a response, the response looked correct, and the customer got false information about their own order.

### Matching the mechanism to the data
Use module one's distinct terms as your decision tool. Reference knowledge that changes slowly, and that's too big for the prompt, goes to retrieval. A small, stable body of knowledge that every call needs can sit directly in the prompt, especially as a cached prefix. Persistent application state, such as order status, balances, inventory and ticket queues, is owned by your system, and the model reaches it only through a tool call. And continuity across turns or sessions is application-managed memory, stored by you and passed back in.

The feasibility lens from module two says the same thing from another angle. For the knowledge property, bring stable knowledge in with retrieval, fetch live-state data with tool calls, and flag uncertainty on contested claims.

### One assistant, two kinds of question
Many real assistants need both. The triage reference architecture shows how: classify the intent, then route documentation questions to knowledge retrieval, live-state queries like order status or account changes to a transactional API, and high-consequence actions to a human approval layer. Module two's RAG mitigation says the same: separate live-state queries from static knowledge queries.

### Exam signals
If a scenario says answers are fluent but contradict the database, or shift after each re-index, the answer is a tool call to the system of record. If it offers a shorter refresh interval, a better embedding model or a higher threshold, those are the traps. And if the data is a stable manual or policy set, retrieval is right, and the question is probably about chunking or indexing instead.

narration:
### Keep the three layers separate
Module one insists on vocabulary before selection. Three terms are often used interchangeably, but they sit at different layers. The entry point is how a user reaches Claude: Claude dot A I, Claude Code, Claude Cowork, Claude in Chrome, Claude for Excel. It's chosen for the user and the work. The build-time interface is what engineers code against: the direct API, the SDKs, MCP and the Agent SDK. It's chosen for the engineering team and the integration. The delivery route is where API traffic terminates: the Anthropic first-party API, AWS Bedrock, Google Cloud Vertex AI or Microsoft Foundry. It's chosen for cloud commitments and compliance posture. Every deployment involves all three, and a decision in one rarely dictates the others. Confusing them is the most common source of muddled architecture conversations.

### The build-time interfaces
The direct API is the HTTP interface. The team owns everything: retries, streaming, tool use, observability and the UI. Maximum control, maximum responsibility. The SDKs, in Python, TypeScript, Java, Go, Ruby, C sharp and PHP, offer the same capability with language-native types and helpers for authentication, retries, streaming and tool-use plumbing. Any agent loop is still the partner's own code. The SDK is the default for embedding Claude in a product; you drop to raw HTTP only when a new API feature hasn't reached the SDK yet. MCP is an open protocol for exposing tools, prompts and resources from one server, so any MCP-aware client can discover and use them. It's a sharing convention across products, not a calling convention inside one. And the Agent SDK runs a managed agent loop, the same loop that powers Claude Code, from the partner's own application code. It handles iteration, tool execution and termination, in TypeScript and Python, at the cost of fine-grained control over each step.

### MCP versus API tool use
These are different layers, not alternatives. API tool use is how Claude calls a tool inside a single request. MCP is how a tool entry point is exposed and discovered across multiple clients, and under the hood an MCP server's tools are called through ordinary tool use. So the choice is about reuse. Pick MCP when one tool entry point must be reachable from several Claude clients, such as Claude dot A I, Claude Code and an internal app. Pick raw tool use when the tools live inside one product. Module two adds the trade-off: MCP keeps the integration layer separate from orchestration, but adds a protocol layer that makes debugging tool calls more complex than direct function calls. If only one client will ever use it, MCP is overhead without payback.

### Claude Code versus the Agent SDK
Claude Code is for developers doing real engineering work, in a terminal, IDE plugins, desktop or the web. Module two is explicit that it isn't a backend for multi-user or customer-facing products. Product integrations use the API, an SDK or the Agent SDK. The Agent SDK is the answer when Claude must act across multiple turns inside the partner's own product, with the partner's application controlling the workflow, and the Claude Code CLI is the wrong shape. The module's summary is the decision rule: one request, one response, use the API or SDK; reusable tools across clients, use MCP; multi-turn action inside your own product, use the Agent SDK.

### The bank case
Module one's case shows every mistake at once. A regional bank wanted an operations assistant for branch staff: look up balances, schedule appointments, answer policy questions. The proposal ran Claude Code on branch laptops with a CLAUDE dot M D file per branch, MCP servers for the customer database, appointments and policy corpus, and subagents doing compliance checks on every interaction. Three failures. The entry point was chosen before the user was named; branch staff don't run terminals. MCP was carried forward from a previous project; there were no other Claude clients in the bank to reuse those tools. And compliance, the highest-consequence path, ran on subagents, which give weaker deterministic guarantees than server-side code. The fitting architecture was a custom web app calling the API, authenticated through the bank's SSO, with compliance in deterministic server-side code and tool calls audited at the server boundary.

### Delivery routes
The delivery-route rule is about what the partner has already committed to, not capability; the model behaves the same on every route. A committed AWS agreement points to Bedrock, with IAM and spend under the existing contract. GCP points to Vertex AI, Azure to Foundry. The first-party API fits when there's no strong cloud preference, the partner wants new features as soon as they ship, or wants to keep AI spend with Anthropic. The trade-off: routes through a cloud provider tend to lag the first-party API on new features. Module four adds that multi-platform designs need an entry-point-responsibility map, saying which entry point owns which task and why, written before integration begins.

### Agent to agent: a source gap
The exam objective also names agent-to-agent connections. The modules cover only orchestrator-to-subagent delegation inside one system, and there's no Anthropic guidance on cross-system agent protocols in the supplied material. So treat this as a source gap. The inferred principle the guide uses is the same as for MCP: introduce a protocol between agents only when independent agents genuinely need to interoperate across system boundaries. Inside one system, the orchestrator and subagents with structured results are simpler and easier to audit.

## Part 3.8 – Evaluate progressive discovery vs. monolithic context strategy
minutes: 9
concepts: Monolithic vs. progressive; staged context; just-in-time loading; Skills invoked on demand; subagents with isolated contexts; tool search and deferred loading; reconstructability trade-off; caching vs. mutation
example: An agent with 60 tools and a 40-page standing instruction set loaded everything up front on every call, so cost grew and accuracy fell. Moving procedures into Skills loaded on demand, deferring rarely used tools, and keeping a small cached core prefix cut input tokens while the eval held.
decision: Default to progressive discovery for multi-turn and agentic work, load only what the next step needs, and keep a small monolithic core where caching or simultaneous access to all the material pays off.
takeaway: Load what the next step needs, not everything the system might need. Keep the stable core small, cached and monolithic.
sources: [MODULE 1] Model & Context Strategy – context strategy spectrum, combined strategies, cost callout; Claude Code customisation layers (Skills on demand, subagents) · [OFFICIAL ANTHROPIC DOCS] Tool search tool; Agent Skills progressive disclosure (approved gap fill) · example is illustrative [INFERENCE]
narration:
### The same spectrum, applied to capabilities
In episode two you saw the context strategy spectrum, from monolithic to progressive. This objective applies the same idea to capabilities as well as data. Monolithic means loading everything the system might need into the prompt up front: all instructions, all reference material, all tool definitions. Progressive discovery means staging it: loading only what the next step needs, and letting the system discover and pull in the rest when it becomes relevant.

### Why monolithic breaks
Module one is clear about where monolithic earns its place: bounded tasks with predictable input size, stable prefixes that benefit from caching, single-shot questions, and reasoning that needs simultaneous access to all the material. It's also clear about where it breaks. In conversations and tool loops, context accumulates turn over turn. Cost and latency scale linearly with input length. Attention quality can degrade on very long contexts well before the hard limit. And the window fills silently before anyone notices something has been truncated. Long-lived deployments built monolithically tend to degrade as the conversation accumulates. The cost callout gives the shape: a four-thousand-token prompt carrying eighty thousand tokens by turn thirty.

### Why progressive wins by default
Progressive context carries forward only what the next step needs. The module calls it the right default for most production workloads: multi-turn dialogue, agent loops that depend mainly on recent state, and workflows that break into stages with narrow handoffs. The glossary defines it as context, instructions or capabilities loaded in stages as the work needs them. That definition covers more than retrieved documents. It shows up in Skills that load reference files on demand, and in agents that gather information through tool calls instead of receiving everything in the first prompt.

### Progressive discovery in Claude Code
Module one's Claude Code layers give you concrete mechanisms. CLAUDE dot M D is the monolithic part on purpose: a file loaded at session start with standing instructions and conventions that apply to every task. Skills are the progressive part: markdown-defined procedures Claude Code invokes on demand rather than loading up front, which keeps the main context lean. Subagents add isolation: helpers with their own context window for bounded tasks like code review or codebase exploration that would otherwise clutter the main thread. Together, they're a small monolithic core with on-demand capabilities and isolated contexts.

### Progressive discovery of tools
The modules don't cover large tool catalogues, so the guide fills that from Anthropic's docs. The tool search tool lets you mark tools as deferred. Claude searches the catalogue and loads only what the current task needs. You still send full definitions; deferred loading controls what enters context. Keep the three to five most-used tools loaded, and never defer the search tool. Anthropic's engineering material on Agent Skills describes the same principle for Skills: only a short description is visible up front, and the full instructions and files load when needed.

### The trade-offs of progressive
Progressive isn't free. Module one lists its weak points. Tasks needing long-range coherence across the full history suffer. Decisions can depend on detail dropped in an earlier turn. Caching is harder when carried-forward context mutates each turn. And the exact input the model saw at step N is no longer easy to reconstruct, which complicates debugging. That last point connects to observability: if you stage context, log what was loaded at each step.

### Combine them deliberately
The answer is rarely all of one. The coding-agent example from episode two is the model: a small, stable monolithic prefix for caching, progressive recent state, just-in-time retrieval for things not preloaded, and compaction when early exploration fills the window. Ask the four questions: what's needed at the start, from recent steps, on demand, and what can be compressed? Context strategy and context sizing are separate decisions; treating them as one is where most designs go wrong.

### Exam signals
If a scenario describes cost growing turn over turn, accuracy falling as more instructions and tools were added, or a context window filling silently, think progressive discovery: Skills on demand, deferred tools, subagents for isolated work, and a small core. If it describes a bounded single-shot task with a large stable document that every call needs, monolithic with caching may be exactly right.
