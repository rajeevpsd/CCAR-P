# Episode 2 – Claude Models, Prompting & Context Engineering
intro: Episode two covers models, prompting and context engineering, thirteen percent of the exam. Five parts: choosing a model tier, designing prompts as reusable assets, picking the right technique, managing the context window, and reusing prompts through caching and Skills.

## Part 2.1 – Select appropriate Claude models based on trade-offs
minutes: 6
concepts: Opus, Sonnet, Haiku; Sonnet default; eval-gated swaps; pre-set rollback criteria; per-step tiering; extended and adaptive thinking; version pinning
example: A Sonnet to Haiku migration averaged 0.86, but two document types fell below the pre-set 0.85 floor. Those two stayed on Sonnet and the rest moved to Haiku.
takeaway: Start with Sonnet. Every move up or down is a release, gated by an eval with a threshold you set in advance.
narration:
The Claude family has three tiers. Opus is the most capable, Sonnet balances capability, speed and cost, and Haiku is the fastest and cheapest.

The default starting point is Sonnet. Move up to Opus only when an eval shows Sonnet misses your quality bar. Move down to Haiku only when an eval confirms the quality trade-off is acceptable.

Treat every model change as a release. You need a representative test set, a grading function, and a pass threshold, and you set that threshold before you run anything. Look at scores per category, not just the average. A downgrade can look fine on average while failing badly on two document types. That's when a partial migration makes sense.

Not every step needs the same model. Classification might run on Haiku, summarisation on Sonnet, and only the final answer on Opus.

Extended thinking is a cost and latency trade-off. Thinking tokens are billed as output, so turn it on only when an eval shows an accuracy gap that prompt work couldn't close.

And pin your model versions, so a silent roll-forward never surprises an auditor.

check: When should the rollback threshold be set? || A) After seeing the results || B) Before running the eval || C) After launch || D) Never || answer: B || why: Setting it afterwards just writes acceptance criteria to fit the data.
check: When is extended thinking justified? || A) Always, because extra reasoning can't hurt quality || B) On every routing classifier to improve its accuracy || C) When an eval shows an accuracy gap after prompt work || D) Whenever the latency budget has room to spare || answer: C || why: It adds billed tokens and latency on every call.

## Part 2.2 – Design system prompts, templates, and guardrails
minutes: 6
concepts: Role and scope; constraints; output contract; templates with fixed scaffolding; Description competency; underspecification; structural guardrails
example: A support-reply template caches role, tone, contract and a no-refund-promise rule, with slots only for the ticket and the manual section. The output contract has no field where a commitment could go.
takeaway: A system prompt reused at scale is an asset you design. Make the safe path the default path, and remember that a prompt alone isn't enforcement.
narration:
At enterprise scale, a system prompt isn't a sentence you type. It's an asset hundreds of requests a day depend on, so it needs structure.

State the role and scope: what's in bounds and what's out. List the constraints: what Claude must always do and must never do. And define the output contract, the exact shape the response has to take.

A template takes that further. It has fixed scaffolding that carries the safety and consistency guarantees, plus slots for the content that changes. Filling a slot should never be able to remove a constraint. The person using the template supplies the variable content and inherits the guardrails automatically.

The skill here is called Description: telling the model precisely what you want. The failure it prevents is underspecification. Wherever the prompt is silent, the model fills the gap, differently each time. So read your prompt asking, for each requirement, is this actually stated, or am I just hoping for it?

Finally, put important guardrails into the structure of the output, not just the role text, and back them with runtime screening. A rule stated in prose can be drifted past.

check: What should a template's fixed scaffolding guarantee? || A) That filling slots can't remove constraints || B) Lower cost on every request || C) Faster responses for users || D) Fewer tokens in each prompt || answer: A || why: The safe path should be the default path.
check: How do you enforce "never promise refunds" most robustly? || A) Repeat the rule several times in the role text || B) Move the rule to the very end of the prompt || C) Build it into the output contract and add screening || D) Raise max_tokens so every rule can be followed || answer: C || why: Structural constraints are harder to drift past than prose.

## Part 2.3 – Apply prompt engineering techniques
minutes: 5
concepts: Zero-shot first; few-shot for hard-to-describe formats; chain-of-thought for multi-step reasoning; deterministic computation for precision; balanced examples; re-tune per model
example: A 12-category classifier confused two categories zero-shot. Two balanced examples per confusable pair fixed it, while chain-of-thought added latency for no gain.
takeaway: Use the lightest technique that meets the requirement. Each step adds tokens and latency.
narration:
There are three core techniques, and you should reach for them in order.

Zero-shot is instruction only. Try it first for any well-specified task.

Few-shot adds a handful of input and output examples. Use it when the format or the judgement is easier to show than to describe. But keep the examples balanced across the cases the system will really see. If every example shows the same kind of answer, you've built bias into the prompt. The same goes for leading phrasing, like "confirm this applicant qualifies".

Chain-of-thought asks the model to reason step by step before answering. It helps with multi-step logic, but it's a tax on every call, so don't use it where it doesn't move accuracy.

And for precise arithmetic, like totals with discounts and tax, don't rely on reasoning at all. Let code execution or a deterministic service own the number.

One more point. Prompts and models ship as a pair. A more capable model often needs less scaffolding, so when you change tiers, re-tune the prompt and evaluate the pairing.
check: Which technique should you try first on a well-specified task? || A) Chain-of-thought || B) Few-shot with twenty examples || C) Fine-tuning || D) Zero-shot || answer: D || why: Start light and escalate only on evidence.
check: The format is hard to describe but easy to recognise. Which technique fits? || A) Chain-of-thought reasoning || B) Balanced few-shot examples || C) A lower temperature setting || D) A larger max_tokens value || answer: B || why: Show, don't tell.
check: Pricing totals with tax are often wrong. What's the best fix? || A) Tell the model to double-check its arithmetic || B) Add examples showing correctly computed totals || C) Let code or a pricing service compute the totals || D) Switch to a bigger model that does better maths || answer: C || why: Deterministic computation should own the number.

## Part 2.4 – Optimize context windows and manage token usage
minutes: 6
concepts: Hard edge; 400 vs. 413 vs. context-window stop; usage field and token counting; budget below the ceiling; skewed distributions; application-managed memory
example: A legal chat started truncating late in sessions. Compacting old turns while keeping clause IDs, retrieving clauses on demand, and caching the policy prefix fixed it.
takeaway: Count tokens, budget with margin, and remember the model has no memory between calls unless your application provides it.
narration:
The context window is the model's working memory, and it has a hard edge. Inside it, everything is available. Outside it, nothing exists.

There are two different ways to hit that edge, so know them apart. If the request itself is too big, the API rejects it before generation. Too many tokens gives a four hundred error. Too many bytes gives a four thirteen. But if the request fits and the response runs into the ceiling while it's generating, you get truncated output with a context-window stop reason.

Don't estimate tokens from characters. Measure them, using the usage field on every response and the token-counting API before you send. Then budget for the largest realistic conversation, plus retrieved context, plus the system prompt, plus scratch space, plus margin. The window is a ceiling, not a target.

Watch the distribution too. Most requests may be short, but a tail of long ones can drive most of your cost.

And keep your terms straight. Retrieval brings knowledge in. Live state comes through tools. And memory between sessions isn't a model feature. Your application stores it and passes it back in.

check: How should you size context? || A) Four characters per token, designed to 95 percent || B) Measure with usage and token counting, and leave margin || C) Watch the monthly bill and adjust from there || D) Use the biggest window available and stop worrying || answer: B || why: Measure, and treat the window as a ceiling.
check: The assistant greets returning users by name. Why? || A) The model has native memory of past users || B) The model was fine-tuned on each returning user || C) Prompt caching stores user preferences between sessions || D) The application stores state and passes it back || answer: D || why: Continuity is managed by the application.

## Part 2.5 – Implement prompt reuse strategies
minutes: 6
concepts: Cache breakpoint; static before dynamic; TTL and write cost; prompt library vs. Skill; container.skills and the Code Execution Tool; progressive disclosure
example: A team's cache never hit because the per-request document came before the fixed instructions. Reordering fixed it.
takeaway: Put fixed content first and cache it. Package repeatable, distributed, governed procedures as versioned Skills.
narration:
When the same long instructions go out on every request, prompt caching is your biggest lever. The cache works on a stable prefix, so order matters. Put the fixed content first, mark a breakpoint, and put the per-request content after it. If dynamic content comes first, the prefix changes every time and the cache never hits.

Caching isn't free. Writing to the cache costs more than normal input, and entries expire. The default lifetime is five minutes, so a prompt called a few times a month may never earn back the write. Model the economics: how often it's called, how big the prefix is, and how often it changes.

For reuse across a team, you have two options. A modular prompt library is a set of fragments engineers assemble in their own code. It's flexible and lightweight. A Skill is a versioned, self-contained unit that packages a procedure, its instructions and any scripts, so it can be governed and rolled back.

On the API, Skills attach to requests and need the Code Execution Tool, which brings a sandboxed execution dependency. And Skills load progressively: metadata first, full content only when needed.

check: When might caching cost more than it saves? || A) A long prefix that's called constantly || B) A static policy document that's called often || C) A small prefix called a few times a month || D) A stable system prompt reused all day || answer: C || why: Write overhead isn't recovered at low frequency.
