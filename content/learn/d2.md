## Part 2.1 – Select appropriate Claude models based on trade-offs
minutes: 10
concepts: Opus, Sonnet, Haiku; Sonnet default; eval-gated swaps; test set, grading function, delta threshold set in advance; per-category scores; partial migration; per-step tiering; extended and adaptive thinking; version pinning; context window as part of the tier decision

decision: Start every step on Sonnet; move up to Opus or down to Haiku only when an eval with a threshold set in advance supports the move, scored per category.
takeaway: Start with Sonnet. Every move up or down is a release, gated by an eval with a threshold you set before you run it.
sources: [MODULE 1] Model & Context Strategy – model selection, extended thinking, eval gate, Sonnet to Haiku case, Opus-everywhere case, calculator · [MODULE 2] Sizing; scoping-call case (context window and tier); model version pinning
narration:
### The three tiers
Module one describes the Claude model family as three tiers, each optimised for a different balance of cost, latency and capability. Opus is the most capable, suited to demanding reasoning, advanced coding and research synthesis where Sonnet doesn't meet your quality bar. Sonnet balances intelligence, speed and cost for most production work. Haiku is the fastest and cheapest.

The default starting point is Sonnet. Move up to Opus only when an eval set tells you Sonnet isn't meeting your quality bar. Move down to Haiku only when an eval set confirms the quality trade-off is acceptable for your specific task. The module is emphatic that the decision to move should be measured, not reflexive.

### Every model change is a release
Any change to the model is a change to the system's behaviour, so a swap between two models is a deployment and should be treated as one. At minimum you need three things. A curated test set of prompts with known-good outputs, covering the real distribution of work the system sees. A grading function, either model-graded against a rubric or programmatic where you can express the check in code. And a delta threshold, set in advance, below which you do not ship. Set the threshold before you run the eval. If you set it after, you aren't setting a standard. You're writing the acceptance criteria after the build.

### The worked downgrade
The module walks a downgrade that was done well. A document-intelligence pipeline has run on Sonnet for six months and used its whole budget. The team wants Haiku. They build two hundred and fifty representative documents with hand-validated extraction targets, stratified by document type, and sized so per-type scores stay meaningful, not just the average. Sonnet scores 0.94 on average; Haiku scores 0.86. The variance sits in two document types, at 0.71 and 0.74. The rollback criterion, set in advance, said that if any single document type drops below 0.85, the migration is rejected. Two crossed the line, so the migration as proposed is rejected. The salvage is a partial migration: route those two types to Sonnet through the existing classifier and the rest to Haiku. Cost drops without taking the regression. The lesson isn't the scores. It's that the criterion was fixed before the data came in, so the team didn't negotiate with itself, and the per-category view surfaced an option a single average would have hidden.

### The cost of not choosing
The second case is the opposite. When the demo has to land, use the best model sounds smart and needs no eval. Ninety days after launch, monthly cost was seven times the model, median latency was 2.3 seconds against an 800-millisecond target, and customer satisfaction hadn't moved. Every call used Opus. There was no per-step model selection, because there was no per-step eval to justify one. Cost was reviewed monthly, so the gap surfaced weeks after launch. And extended thinking had been switched on for a routing classifier that needed no reasoning at all. The fix: build the eval set retroactively, route the classifier to Haiku, route mid-pipeline summarisation to Sonnet, and keep Opus only on final response composition, where the eval said it earned its place. Cost fell seventy-one percent, median latency fell to 940 milliseconds, and satisfaction held. Remember the line: not choosing a model is equivalent to choosing the most expensive one. The eval set isn't just a release gate. It's the only thing that makes the tier decision defensible during design.

### Extended thinking
Extended thinking lets the model work through a problem in a separate block of thinking tokens before the final answer. Module one explains how the control has changed. On Claude Opus 4.6 and later, Sonnet 4.6 and later, and Sonnet 5, adaptive thinking with the effort parameter is the recommended control: you set how much reasoning effort to apply rather than a token budget. Adaptive thinking is the only mode on Claude Fable 5. The older budget tokens setting is deprecated on the 4.6 generation and removed on Sonnet 5, where it returns a 400. The module itself tells you to verify current support at publish time. Thinking tokens are billed as output tokens and add latency. When thinking isn't engaged, none are generated or billed. The API may return a summarised view of the reasoning, but you are billed for the thinking tokens actually used, not the length of the summary. The rule: run evals without it first, work on the prompt, and enable thinking only for a measured accuracy gap. It can't hurt is not evidence.

### Context window as part of the tier decision
Module two's scoping case adds one more dimension. Whether a three-hundred-page contract fits in one call depends on the tier's context window. A one-million-token window can take it without chunking; a two-hundred-thousand-token window may need a chunking strategy for the longest documents. So context capacity is part of the tier decision, not a settled assumption.

### Pin the version
Finally, model version pinning applies to every architecture. Pin versions in configuration, watch the deprecation page, and keep a version-update runbook. The ninety-day retrospective in episode one showed what happens otherwise: an auditor asked which version approved a disbursement, and it had rolled forward two weeks earlier without re-validation.

## Part 2.2 – Design system prompts, templates, and guardrails
minutes: 9
concepts: System prompt as an enterprise asset; role and scope, constraints, output contract; templates with fixed scaffolding and parameterised slots; Description competency (scope, format, constraints); underspecification; structural guardrails; instructions are not enforcement
example: A support-reply asset: role, tone rules, output contract and the never-promise-a-refund rule form the stable prefix; the ticket and manual section are the only per-request content; the refund rule is a constraint in the output contract, not a sentence in the role text; it ships as a versioned Skill.
decision: Build guardrails into the fixed scaffolding and output contract so filling a slot can't remove a constraint, and pair prompt instructions with runtime controls for anything that must be enforced.
takeaway: A reused prompt is an asset with a role, constraints and an output contract. Where the prompt is silent, the model improvises, differently each time.
sources: [MODULE 1] Prompting as Architecture – system-prompt architecture, templates, Description, underspecification; Author the reusable prompt asset (exercise) · [MODULE 3] Alignment – system-prompt instruction layer and its blind spot
narration:
### From sentence to asset
At enterprise scale, a prompt isn't a sentence you type. Module one calls it an asset you design: a system prompt, a reusable template, and the guardrails that keep both safe and consistent. A system prompt for a one-off chat and a system prompt that hundreds of requests a day depend on are different artifacts. When a prompt is reused at scale, ambiguity becomes a defect multiplied across every request.

### The structure of an enterprise system prompt
The enterprise version has structure. A clear statement of role and scope. The constraints the model must hold, meaning what it must never do and what it must always do. And an output contract, naming the exact shape the response must take. Those three pieces are what let you test the prompt, review it, and know when a change has broken it.

### Templates: the safe path as the default path
A template is a system prompt with parameterised slots, the parts that change per request, and fixed scaffolding around them. The design goal is that the fixed scaffolding carries the consistency and safety guarantees, so that filling a slot can't accidentally remove a constraint. A well-designed template makes the safe path the default path. The person using it supplies the variable content and inherits the guardrails without having to re-author them. Templates also concentrate complexity in one place where it can be reviewed and governed, instead of scattering it across ad-hoc prompts that nobody owns.

### Description: say what you mean
Description is one of the four AI Fluency competencies, the discipline of telling the model precisely what you want. Applied to prompt design, a well-described prompt names three things. The scope: what's in bounds and what's out. The format: the exact output contract. And the constraints: the rules that must never be violated. The failure to watch for is underspecification. It's a gap the model fills with its own assumption, and it fills it differently each time. That's exactly the non-determinism you don't want in a reused asset.

### Diagnosing underspecification
The architect's skill here is reading a prompt for what it fails to say. For each requirement the output must meet, ask whether the prompt actually states it, or merely hopes for it. Where the prompt is silent, the model improvises. The fix is to make the implicit explicit: restate the goal alongside the instruction, name the format, and bound the constraints. This connects back to steerability from episode one. Claude follows concrete, verifiable instructions well, and drifts on abstract ones.

### Structural guardrails beat stated ones
Module one's exercise is worth rehearsing. A support organisation drafts replies hundreds of times a day from a ticket and a manual section. Replies must follow tone guidelines, cite the manual section used, and never promise a refund or timeline the agent hasn't approved. Three decisions. First, the cache breakpoint: role, tone rules, output contract and the never-promise rule go first as the stable prefix; the ticket and the manual section are the only per-request content. Second, the guardrail: build it into the output contract as a structural constraint the format requires, not a sentence in the role text. A rule stated in the role can be drifted past; a constraint built into the output contract shapes the response format and can't be quietly ignored. Third, packaging: a versioned Skill, because the procedure is stable, runs identically across the support org, and needs versioning and rollback. A pasted template each agent keeps locally drifts into slightly different versions.

### Instructions are not enforcement
Module three adds the boundary you must respect. The system prompt is one layer in the safety stack. It reliably covers role, tone and stated constraints inside one request. It doesn't cover anything an adversarial or unusual input can talk Claude out of, because instructions are not enforcement. So system instructions shape behaviour, but deployment-specific policy is enforced only when those instructions are paired with runtime controls: screening, authorisation and review. And the risk callout from module one bears repeating. An underspecified guardrail is worse than a missing one, because it creates the appearance of a control without the substance. A constraint the model can quietly route around is not a constraint.

### The economics
A vague system prompt is paid for in every request that needs correction, retry or human clean-up. Designing it well once is far cheaper than diagnosing drift across thousands of calls.

## Part 2.3 – Apply prompt engineering techniques (zero-shot, few-shot, chain-of-thought)
minutes: 8
concepts: Zero-shot first; few-shot when easier to show than describe; chain-of-thought for multi-step reasoning; lightest technique that meets the requirement; behaviour differs across models; prompt-model pairing; bias in prompt construction; balanced examples; maintenance of examples
example: A ticket classifier was given chain-of-thought "to be safe". An eval showed no accuracy gain but higher latency and output tokens. Zero-shot with a strict label set met the bar; few-shot was reserved for the one ambiguous category, with balanced examples.
decision: Start zero-shot, add examples only when the format or judgement is easier to show than to describe, and add explicit reasoning only when the task's structure demands it.
takeaway: Use the lightest technique that meets the requirement. Each step up adds tokens and latency on every call.
sources: [MODULE 1] Prompt engineering techniques across models – technique selection, behavioural differences, avoiding bias, technique-selection checkpoint; Try prompting before fine-tuning; four properties (steerability); example is illustrative [INFERENCE]
narration:
### Technique follows task complexity
Once a prompt is designed for reuse, the next question is which technique to use inside it. Module one is clear that the technique is chosen by the complexity of the task, not by habit. There are three main techniques.

Zero-shot means instruction only, with no examples. It fits well-specified tasks the model already handles reliably, and it's the default to try first.

Few-shot means a handful of input and output examples in the prompt. It fits tasks where the desired format or judgement is easier to show than to describe. If you find yourself writing three paragraphs explaining a tone, two good examples might do it better.

Chain-of-thought means prompting the model to reason step by step before it answers. It fits multi-step reasoning, arithmetic-like logic, or tasks where the path matters to the answer.

### The deliberate progression
The progression is deliberate. Start zero-shot. Add examples only if the task needs them. Add explicit reasoning only if the task's structure demands it. Each step adds tokens and latency, so reach for the lightest technique that meets the requirement. The cost callout in the module puts it bluntly: chain-of-thought on a task that doesn't need it is a recurring tax for no gain. And this sits inside the bigger sequence from episode one: optimise the prompt, then add tools or retrieval, then a stronger pattern like evaluator-optimizer, and only then consider fine-tuning.

How do you know which step you need? The same way you know anything in this course: measure. Run the zero-shot version against your eval set. If it meets the threshold, stop. If it fails in a pattern, say, wrong output shape, try a few examples. If it fails on tasks with several dependent steps, try explicit reasoning. Each move should be tied to a failure you observed.

### Same prompt, different model
The same prompt doesn't behave identically across model tiers or generations. A more capable model may need less scaffolding, fewer examples and less step-by-step instruction, to reach the same quality. A less capable model may need more. So a prompt tuned for one model is a starting point for another, not a finished artifact. This is why a model swap is gated with an eval: the prompt-and-model pairing is what you're actually shipping. If a team swaps Sonnet for Haiku and keeps the prompt unchanged, the eval may reveal that Haiku needs an extra example or a tighter output contract.

### Bias can be built into the prompt
Prompt construction can introduce bias the task never intended. The module names three sources. Leading phrasing that suggests an answer. Unbalanced examples, few-shot sets that show only one kind of case. And assumptions baked into the instruction itself. All of them steer output in ways that are easy to miss. The discipline is to phrase neutrally, balance examples across the cases the system will actually see, and check whether the prompt presumes an answer it should be eliciting. The risk is that bias introduced in the prompt is invisible in any single output and only shows up in aggregate. That's why neutral phrasing and balanced examples are a design requirement, not a polish step. You'll meet this again in episode five, where prompt framing and few-shot examples are two of the four places unequal outcomes can enter a system.

### Examples are content to maintain
Few-shot examples come with a maintenance cost. As the task evolves, stale examples quietly steer the model in the wrong direction. Treat them like code: version them, review them when the task changes, and include them in what the eval covers.

### Steerability ties it together
This all traces back to the steerability property. Claude does well with short, concrete, verifiable instructions with defined formats and clear roles. It drifts on abstract instructions, long reasoning chains and precise computation. So the technique choice is a steerability decision. Be concrete first. Show, if describing fails. Ask for reasoning when the path matters. And for precise arithmetic, don't prompt harder: let code or a tool compute the answer.

## Part 2.4 – Optimize context windows and manage token usage
minutes: 10
concepts: Context window, retrieval, persistent application state, summaries and memory layers; tokens measured, not estimated; usage field and token counting; budget for the largest realistic case plus margin; monolithic, progressive, retrieval, compaction; combining strategies; 400, 413 and context-window stop reason
example: A long-running coding agent: a small cached monolithic prefix at session start, progressive recent state during work, just-in-time retrieval for files it didn't preload, and compaction once early exploration fills the window.
decision: Budget for the largest realistic conversation, not the window size, and pick a context strategy per need: what's needed at the start, from recent steps, on demand, and what can be compressed.
takeaway: The context window is a ceiling, not a target. Measure tokens, budget with margin, and combine strategies deliberately.
sources: [MODULE 1] How Claude Behaves – working memory and its two edge errors; Model & Context Strategy – distinct terms, context-window sizing, context strategy spectrum, coding-agent worked example, cost callout · [MODULE 2] Sizing – token budget per request, distribution not average
narration:
### Four terms that get conflated
Module one starts this topic with four terms that are often used interchangeably, and conflating them produces architecture mistakes. The context window is the model's active attention space. Everything inside it is available; everything outside doesn't exist to the model, and it resets between calls unless your application manages continuity. Retrieval is external knowledge fetched at query time. It augments the window; it doesn't replace it, and the model only sees what the retriever surfaces. Persistent application state is owned by your system, not the model: order status, user records, balances. The model needs a tool call to get it. And summaries and memory layers are application-managed continuity across turns or sessions. The model has no native memory between calls, so anything that persists does so because your application stored it and passed it back. That's an architectural choice, not a model capability.

### Measure tokens, don't estimate them
The window is measured in tokens, and how much text a token covers varies by model generation, tokenizer and language. So treat any characters-per-token ratio as a rough illustration. Measure instead. Every API response reports actual token counts in its usage field, and those counts are what the limit and the bill apply to. Everything entering the window counts: the system prompt, conversation history, retrieved documents, tool outputs and the model's own responses. Remember the two edge errors from episode one: an oversized prompt is rejected with a 400 invalid request error, an oversized request body with a 413, and a prompt that fits but whose generation hits the ceiling comes back truncated with a model context window exceeded stop reason. Use the token-counting API before you send.

### Don't budget the full window
The practical rule is direct. Budget for the largest realistic conversation, plus retrieved context, plus system prompt, plus working scratch, plus margin for growth. The window is a ceiling, not a target. Designing toward the ceiling means you'll hit it in production. Module two adds the cost angle: model the token distribution, not the average. Most requests may be short, but a tail of long requests can consume most of the spend.

### The strategy spectrum
Every workload makes a choice about how context reaches the model on each call. At one pole is monolithic: everything in the prompt at once. It earns its place for bounded tasks with predictable input size, stable prefixes that benefit from caching, single-shot questions where retrieval latency isn't worth paying, and reasoning that genuinely needs simultaneous access to all the material. It breaks in conversations and tool loops, where context accumulates turn over turn. Cost and latency scale linearly with input length, and attention quality can degrade on very long contexts well before the hard limit.

At the other pole is progressive: carry forward only what the next step needs, retrieve just in time, summarise across turns. It's the right default for most production workloads: multi-turn dialogue, agent loops that depend mainly on recent state, and staged workflows with narrow handoffs. It breaks for tasks that need long-range coherence, for decisions depending on detail dropped earlier, and it makes caching harder when the carried-forward context mutates. It also means the exact input at step N isn't reconstructable, which complicates debugging.

Two strategies sit between the poles. Retrieval fetches relevant chunks from an external store: great for knowledge bases too large for the window, sources that change faster than you redeploy, and cases needing citations. It breaks on synthesis across many documents scored independently, on chunking that splits tables or code, and on recall failures where the right document never enters the top results. And retrieval quality becomes a system you must evaluate. Compaction periodically summarises accumulated context: good for long-running agents and phase transitions. It breaks when summaries drop load-bearing detail like identifiers, numbers or earlier decisions. The summariser is itself a model call, compaction is largely one-way, and measuring summary fidelity is an unsolved evaluation problem.

### Combining strategies
Production systems almost always combine these. The module's worked example is a long-running coding agent. At session start, a small, stable monolithic prefix with the task and referenced files, ideal for caching. During active work, progressive recent state, since each tool call appends what the next step needs. When the agent realises it needs a file it didn't load, just-in-time retrieval. And when early exploration fills the window, compaction that keeps what was tried and learned. No single strategy could carry that workload. So ask four separate questions. What does the model need at the start? That's your monolithic baseline. What does it need from recent steps? That's the progressive window. What might it fetch on demand? That's the retrieval layer. What can be compressed without losing decision-relevant detail? That's the compaction policy. And remember that context strategy and context sizing are separate decisions that interact. Treating them as one is where most designs go wrong.

### The silent budget killer
Module one's cost callout is a number worth remembering: a conversation that starts with a four-thousand-token prompt can be carrying eighty thousand tokens by turn thirty. Per-call cost grows with the conversation, and there's no visible signal until the bill arrives.

narration:
### Why reuse is its own decision
Reusable prompts raise questions a one-off prompt never does. How do you reuse them efficiently, and how do you package them so a team can share and govern them? Module one answers with two tools: caching for efficiency, and the choice between a modular prompt library and a Skill for packaging.

### A cache that never hits
Start with the cautionary case. A team put a reusable analysis prompt into production and saw none of the savings caching should bring. The cause was ordering. They placed the per-request content, the document being analysed, at the top of the prompt, above the large fixed instruction block. The cache matches on a stable prefix, so putting dynamic content first meant the prefix changed on every request and the cache never hit. The fix was to reorder: fixed content first, dynamic content last.

### Caching mechanics an architect designs around
Four mechanics. Cache breakpoints: caching works on a stable prefix, so mark the boundary between the fixed, cacheable part and the variable part, and keep the fixed part genuinely fixed. Content ordering: static before dynamic, always. TTL selection: match the cache lifetime to how often the fixed content changes and how often the prompt is called. A prompt called constantly benefits from a longer-lived cache; one called rarely may never pay back the write. And the write overhead: writing to the cache has its own cost, so for a prompt called infrequently or with a small fixed portion, caching can cost more than it saves. Caching is a design decision, not a default.

Module two adds the operational details. Caching needs explicit cache control markers in the request. Cache writes cost more per token than standard input, so the cost model must include the write on first use. The default TTL is five minutes, so workloads whose requests arrive less often than that won't see consistent savings. Reads are much cheaper; the module illustrates ten percent of the input rate and tells you to confirm current pricing. And the response is identical with or without caching. What's stored is the processed prompt prefix, so there's one more risk: if cached content must reflect live state, caching creates a consistency window that may break the use case.

### Modular prompt library or Skill
There are two ways to make a prompt reusable across a team. A modular prompt library is a shared collection of fragments and templates that engineers assemble in their own code. A Skill is more formal: a versioned, self-contained unit, a SKILL dot M D file that packages the instructions, optional executable scripts and version management, so the procedure travels as one governed artifact.

Choose with three considerations. Repeatability: an assembled, often-tweaked prompt leans to a library; a stable procedure run the same way every time leans to a Skill. Distribution: shared within one codebase or team leans to a library; distributed across teams or products leans to a Skill. Governance: lightweight ownership of fragments leans to a library; a need for versioning, approval and rollback leans to a Skill, because Skills carry that. The risk on the other side is drift. An ungoverned prompt copied across teams becomes many slightly different versions, each with its own quietly different behaviour. Versioned reuse is the control.

### Skills as an integration mechanism
Skills aren't only packaging. Module one notes they're an integration mechanism. A Skill can be attached to a request through the container dot skills parameter, published and versioned through the v1 skills endpoint, and managed under version control like any deployed asset. Skills require the Code Execution Tool to run, so the integration carries a sandboxed execution dependency. When the question is how a reusable procedure reaches Claude across entry points, a versioned Skill is one mechanism to weigh alongside MCP and direct tool use. In Claude Code, Skills are also progressive by design: they're invoked on demand instead of loaded up front, which keeps the main context lean.

### Reuse at team scale
Module five takes reuse to the team. There are four ways to distribute a Skill: an org-provisioned Skill under organisation settings for everyone; a plugin assigned to a group, which gives install preferences, group targeting and version-controlled updates from a connected repository; a Claude Code project Skill that lives in the repository and versions with it; and an API Skill called by the partner's own products, with explicit version pinning. You'll go deeper on this in episode seven. The thread connecting all of it is the same: reuse is only safe when the reused thing has a version, an owner and a way back.
