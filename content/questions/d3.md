# Domain 3 – Integration · Question bank (original practice items, not real exam questions)

## D3-001
objective: 3.1
difficulty: Easy
select: 1
scenario: An internal HR assistant built on the Agent SDK can read policy documents, look up an employee's leave balance, update payroll records, and email any address. HR staff use it only to answer policy and leave-balance questions.
question: Which change most directly reduces risk in line with least privilege?
A: Add a confirmation step before payroll updates and outbound emails so a human confirms each one.
B: Log every payroll update and email so security can review them weekly.
C: Remove the payroll-update and email tools from the agent's configuration.
D: Add a system-prompt rule telling the agent never to modify payroll or email outside the company.
answer: C
why A: A confirmation step is a compensating control; the unneeded capability and its attack surface remain.
why B: Logging is detective. It records misuse after the fact but leaves the unnecessary privilege in place.
why C: Correct. Removing tools the role never uses eliminates the risk at its source and also trims context and eval scope.
why D: A system-prompt instruction is not enforcement; an adversarial input can talk the model past it.
lesson: Capabilities a role doesn't need should be removed, not guarded.
source: M2 Least-privilege tool configuration; EG Sample 1

## D3-002
objective: 3.1
difficulty: Medium
select: 1
scenario: An orchestrator agent fans out contract-section reviews to subagents. Each subagent inherits the orchestrator's full tool set, including tools that file documents to the DMS and send client notifications. Subagents only need to read a section and return findings.
question: What is the best configuration change?
A: Scope each subagent to read-only document access, returning findings to the orchestrator.
B: Keep the inherited tools but require subagents to explain and justify any write action in their findings.
C: Move the DMS and notification tools to a separate MCP server that all agents share, so access is centralised.
D: Upgrade subagents to a more capable model so they choose tools more carefully.
answer: A
why A: Correct. Scoping each subagent's tools to its task creates a trust hierarchy so subagents can't reach side-effecting tools.
why B: An explanation doesn't remove capability; a manipulated subagent can still write or notify.
why C: Moving tools to MCP changes packaging, not who can call them; the privilege remains.
why D: Model capability is unrelated to authorization scope.
lesson: In orchestrator-worker designs, give each subagent only the tools its sub-task needs.
source: M2 Least-privilege tool configuration (trust hierarchy); M1 Multi-agent systems

## D3-003
objective: 3.1
difficulty: Hard
select: 2
scenario: A platform team connects a customer-success agent to 9 MCP servers (about 180 tools). Users report occasional wrong tool choices, and an access review finds the agent can call billing-adjustment tools that customer-success staff aren't authorised to use. Input tokens per request are high.
question: Which TWO actions address both the privilege problem and the context problem? (Select 2)
A: Remove billing-adjustment tools from the agent's configuration because the role isn't authorised for them.
B: Mark rarely used tools with defer_loading and enable the tool search tool, keeping a few frequently used tools loaded.
C: Defer the billing-adjustment tools so Claude only sees them when it searches for them.
D: Switch to a larger-context model so all 180 tool definitions fit comfortably.
E: Add a system-prompt instruction listing which tools the agent must not use.
answer: A,B
why A: Correct. An unauthorised capability must be removed; this is the least-privilege fix.
why B: Correct. Deferred loading with tool search cuts the context spent on definitions and improves tool selection for large catalogues.
why C: Deferring changes what enters context, not what is permitted; a deferred tool can still be found and called.
why D: A bigger window treats the symptom, adds cost, and doesn't touch the privilege gap.
why E: Instructions aren't authorization controls.
lesson: Tool search reduces context bloat; only removal or authorization reduces privilege bloat.

why A: A larger window delays the cliff but keeps linear cost growth and attention degradation.

scenario: An enterprise agent connects 12 MCP servers with about 350 tools. Before any work begins, tool definitions consume a large share of the context window. Usage logs show five tools account for most calls.
question: What is the recommended configuration?
A: Enable tool search with defer_loading on the long tail, keeping the five hot tools loaded.
B: Defer all tools, including the tool search tool, so the initial context is as small as possible.
C: Stop sending deferred tool definitions in the request, sending them only once Claude asks.
D: Split the agent into 12 subagents, one per MCP server, so each holds only its own tools.
answer: A
why A: Correct. Tool search with defer_loading loads tools on demand; keeping the most-used tools loaded avoids a search step on most turns.
why B: The tool search tool itself must never be deferred.
why C: Deferred definitions must still be sent; defer_loading controls what enters context, not what is sent.
why D: Splitting by server rather than by task adds multi-agent cost and failure boundaries without a task reason.
lesson: Progressive discovery applies to tools too: defer the long tail, keep the hot tools loaded.
