# Domain 7 – Developer Productivity & Operational Enablement · Question bank (original practice items, not real exam questions)

## D7-001
objective: 7.1
difficulty: Easy
select: 1
scenario: A 200-engineer organisation wants Claude Code adopted across four departments.
question: Which rollout pattern is recommended?
A: Enable everyone at once with an announcement email and a quick-start guide.
B: A champion per department proves a workflow, then batches follow.
C: Let each engineer configure their own environment however they prefer.
D: Delay rollout until a complete training curriculum has been written.
answer: B
why A: A mass switch-on produces confused first attempts and quiet retreat.
why B: Correct. Champions absorb early friction, build local examples and become first-line support.
why C: Personal setups drift apart; teams need a shared baseline.
why D: Unnecessary delay; champions build the material as they go.
lesson: Champions first, then batches.
source: M5 Roll out through champions, then batches

## D7-002
objective: 7.1
difficulty: Medium
select: 1
scenario: A platform team pushed a release-notes Skill to 40 engineers as a flat bundle. A bad edit broke the output format for everyone and required a manual fix while bad notes kept shipping.
question: Which distribution approach would have prevented this?
A: Email the Skill file to each engineer with installation instructions.
B: An org-provisioned Skill, re-uploaded manually whenever it changes.
C: A group-assigned plugin with versioned updates, rollback and an owner.
D: Remove the Skill and paste the procedure into each engineer's prompt.
answer: C
why A: No versioning or central rollback.
why B: Org-provisioned Skills lack version pinning and native rollback.
why C: Correct. Plugins offer the strongest governance for group-scoped distribution.
why D: That reintroduces copy-paste drift.
lesson: A shared asset with no version and no way back is a liability.
source: M5 "The skill that shipped with no way back"; Skills distribution table

## D7-003
objective: 7.1
difficulty: Medium
select: 1
scenario: A team must guarantee that a security linter runs before every commit Claude Code makes, regardless of what the prompt or CLAUDE.md says.
question: Which configuration layer fits?
A: A hook that runs the linter as a deterministic pre-commit gate.
B: A line in CLAUDE.md telling Claude to run the linter before committing.
C: A Skill that describes how and when to run the linter.
D: A dedicated linting subagent that the main agent can call.
answer: A
why A: Correct. When the guarantee must come from code rather than prompting, use a hook.
why B: CLAUDE.md shapes behaviour but isn't a guarantee.
why C: A Skill is invoked on demand, not enforced.
why D: A subagent's behaviour still depends on the model choosing to run it.
lesson: Shaping layers guide; governing layers (hooks, permissions, sandbox) enforce.
source: M1 Claude Code customization and governance layers

## D7-004
objective: 7.1
difficulty: Hard
select: 2
scenario: Leadership worries that Claude usage across a 300-person engineering org will quietly drift to expensive tiers and overrun budget.
question: Which TWO team-setup controls are most appropriate? (Select 2)
A: Set model defaults and model allowlists/restrictions deliberately rather than inheriting defaults.
B: Configure spend, rate and per-user caps, along with effort guidance.
C: Ban the most capable tier entirely for everyone.
D: Review the bill quarterly and adjust then.
E: Let each engineer choose any model without limits to maximise productivity.
answer: A,B
why A: Correct. Unmanaged model choice can quietly route work to costlier tiers; at team scale it multiplies.
why B: Correct. Caps and effort guidance keep consumption bounded.
why C: A blanket ban removes legitimate high-value uses; allowlists and caps are more precise.
why D: That's too late; set the spend posture before the first bill.
why E: That's the risk being described.
lesson: Set the spend posture during team setup.
source: M5 Set the spend posture before the first bill

scenario: A team ships AI-generated code faster than ever. An incident traces back to a generated change whose author couldn't explain how it handled a particular input.
question: What practice was missing?
A: More AI review tools to catch issues the first reviewer missed.
B: A faster CI pipeline so problems surface sooner after merge.
C: A verification checklist, including human understanding.

## D7-006
objective: 7.2
difficulty: Medium
select: 1
scenario: Six months after providing Claude access, three of forty developers use it heavily, and most others only ask it occasional questions in a chat window.
question: Which two adoption failure modes are present, and what helps?
A: Over-adoption by a few users; restrict their access to spread capacity.
B: Model mismatch; upgrade the tier so more developers find it useful.
C: Cost overrun; add per-user caps so heavy users don't dominate spend.
D: Lumpy adoption and stalling at chat; use champions and workflow integration.

## D7-010
objective: 7.3
difficulty: Hard
select: 1
scenario: A tool integration fails intermittently, mostly at peak. Engineers keep restarting the service. Traces have never been examined.
question: What is the best first diagnostic action and likely cause class?
A: Trace one failed call; check auth, rate limits and errors; back off on 429/5xx.
B: Switch to a more capable model that handles tool calls more reliably.
C: Rewrite the system prompt so the agent calls the tool more carefully.
D: Increase the context window so tool results aren't truncated.
answer: A
why A: Correct. Intermittent tool failures point to auth, rate limits or unhandled error paths; trace one call and apply backoff for transient errors.
why B: Model tier doesn't cause tool rate limits.
why C: The prompt isn't implicated by peak-time intermittent failures.
why D: Unrelated.
lesson: Connect the symptom to its architectural cause before acting.
source: M5 Symptom table (intermittent tool failures); M2 Reliability controls
