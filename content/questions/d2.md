# Domain 2 – Claude Models, Prompting & Context Engineering · Question bank (original practice items, not real exam questions)

## D2-001
objective: 2.1
difficulty: Easy
select: 1
scenario: A team starting a new production build asks which Claude tier to begin with.
question: What is the recommended default, and when should they move?
A: Opus everywhere, moving down only if the monthly budget is exceeded.
B: Haiku everywhere, moving up only if users start to complain.
C: Whichever tier the team's previous project used successfully.
D: Sonnet as the default; move to Opus or Haiku only when an eval supports it.
answer: D
why A: Defaulting to the most expensive tier is the 7× overrun pattern.
why B: User complaints are a lagging, unmeasured signal.
why C: Habit isn't a justification.
why D: Correct. Start with Sonnet; every move is measured, not reflexive.
lesson: Start with Sonnet and move tiers only on eval evidence.
source: M1 Model selection

## D2-002
objective: 2.1
difficulty: Medium
select: 1
scenario: A cost-driven migration from Sonnet to Haiku is proposed. The eval shows an average of 0.94 vs. 0.86. Two document types score 0.71 and 0.74. The pre-set rollback criterion is "no single type below 0.85".
question: What is the right decision?
A: Partial: route the two failing types to Sonnet, the rest to Haiku.
B: Accept the migration, because an average of 0.86 is close enough to 0.94.
C: Reject it entirely and keep every document type on Sonnet.
D: Lower the rollback criterion to 0.70 so the migration can pass.
answer: A
why A: Correct. The pre-set criterion is respected and a partial migration still captures savings.
why B: That ignores the agreed criterion and the per-type failures.
why C: It leaves the available savings on the table.
why D: Changing the threshold after seeing data isn't a standard.
lesson: Set rollback criteria before the data comes in; per-category results show where a partial migration works.
source: M1 Worked case: Sonnet to Haiku downgrade

## D2-005
objective: 2.2
difficulty: Easy
select: 1
scenario: A support-reply system prompt says "Be helpful and professional." Outputs vary widely in structure and sometimes omit required citations.
question: What should the architect add?
A: A longer list of adjectives describing the tone the replies should have.
B: Role, scope, must/must-not constraints, and an output contract with citations.
C: A higher temperature so replies feel more varied and natural.
D: A larger model that can infer the expected structure on its own.
answer: B
why A: Adjectives stay abstract; steerability is weak on abstract instructions.
why B: Correct. An enterprise prompt names its scope, format and constraints; underspecification invites variation.
why C: That increases variance.
why D: A bigger model still has to guess unstated requirements.
lesson: Role, scope, constraints, output contract.

## D2-007
objective: 2.2
difficulty: Hard
select: 1
scenario: A drafting assistant must never promise refunds or timelines. The rule is in the role text, but drafts occasionally include "we'll refund you within 5 days".
question: Which approach most robustly enforces this guardrail?
A: Repeat the rule three times in the role text so the model can't miss it.
B: Make it structural in the output contract, plus output screening.
C: Move the rule to the end of the prompt, where the model attends most.
D: Increase max_tokens so the model has room to follow every instruction.
answer: B
why A: Repetition is still an instruction the model can drift past.

why D: Unrelated.
lesson: Put guardrails in the format's structure, then back them with runtime controls.

## D2-008

scenario: You are reviewing a prompt for underspecification gaps.
question: Which TWO checks best reveal gaps? (Select 2)
A: For each output requirement, check whether the prompt actually states it or only hopes for it.
B: Count the number of words in the prompt.
C: Check whether the prompt restates the goal alongside the instruction where intent and literal wording could diverge.
D: Check whether the prompt names the latest model version, so behaviour matches the current release.

## D2-012
objective: 2.3
difficulty: Hard
select: 1
scenario: A prompt tuned with extensive step-by-step scaffolding for a less capable tier is moved unchanged to a more capable tier. Quality improves slightly but cost and latency rise considerably.
question: What should the team do?
A: Re-tune the prompt for the new tier and evaluate the pairing.
B: Keep the prompt unchanged, since it already worked on the previous tier.
C: Add more scaffolding so the more capable tier performs even better.
D: Revert to the less capable tier without running an evaluation.
answer: A
why A: Correct. More capable models often need less scaffolding; the prompt-model pairing is what you ship, so evaluate it.
why B: A prompt tuned for one model is a starting point for another.
why C: More scaffolding adds cost with no evidence it helps.
why D: An unevaluated revert isn't justified either.
lesson: Re-tune prompts per model; ship and evaluate the pairing.

## D2-013
objective: 2.4
difficulty: Easy
select: 1
scenario: A request returns HTTP 400 invalid_request_error saying the prompt is too long.
question: What does this indicate?
A: The generation hit the context-window ceiling partway through the response.
B: A transient server error that should be retried with exponential backoff.
C: The request exceeded the token limit and was rejected before generation.
D: The request body exceeded the API's maximum byte limit.
answer: C
why A: That shows up as a model_context_window_exceeded stop reason with truncated output, not a 400.
why B: A 400 isn't transient; retrying the same request fails again.
why C: Correct. An oversized request is rejected before generation with a 400.
why D: A byte-limit breach returns 413 request_too_large.
lesson: Distinguish 400 (tokens), 413 (bytes) and a mid-generation context-window stop.
source: M1 Working memory
